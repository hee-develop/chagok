# 도착 횟수와 자주 가는 곳 후보

차가 장소에 도착하면 서버가 그 자리의 장소별 **도착 횟수**를 +1하고, 도착 횟수가 많은 곳을 '어디로 갈까요?' 후보로 올립니다.
정책서 6장 '도착'(장소 도착 횟수 +1), 8장 끝 문단(자주 가는 곳 후보 세 출처, 1순위는 도착 횟수가 가장 많은 곳, 지금 집이면 집은 뺌), 11장 '도착 횟수'(자리별 장소·횟수·마지막 날짜, 사용자가 지우거나 자리가 지워질 때까지), 12장 '자주 가는 곳 기준 — 도착 3회 넘게'를 따릅니다.
이 묶음은 **서버만**입니다(차 앱이 도착 때 `POST /arrivals`를 부르는 것, 후보 표시, 폰 화면은 다른 묶음).

## 저장하는 것

- 자리(`SeatData.arrivals`, `server/src/arrivals.ts`)마다 장소 목록: `{ id, name, address, lat, lng, count, lastDate }`. **장소·횟수·마지막 날짜(서울 `YYYY-MM-DD`)뿐**이고 이동 경로·도착 시각 이력은 저장하지 않습니다(그래서 요일·시간대 패턴은 쓰지 않습니다, 정책서 8장).
- 같은 일정의 도착을 두 번 세지 않으려고 **일정 id와 처음 센 `at`의 서울 날짜**만 짧게 기억합니다(정책서 11장 '일정 상태 — 그날까지'). 처음 센 날짜가 4일(`ARRIVAL_KEY_DAYS` = `at`을 받는 범위 3일 + 날짜 경계 하루) 넘게 지나거나 500개(`MAX_ARRIVAL_KEYS`)를 넘으면 오래된 것부터 잊습니다. 보관 기간이 `at`을 받는 범위(3일 전)보다 짧지 않아, 3일 전 `at`으로 센 도착도 같은 `at`으로 다시 와 있는 동안은 중복으로 세지 않습니다. 이 기억은 정기 작업 `purge-expired`(매일 새벽)에서도 정리됩니다(도착 횟수 자체는 지우지 않음).
- 메모리 저장이라 서버를 다시 켜면 사라집니다. **연결 끊기·차곡 초기화·무소식 정리로 자리가 지워지면 함께 지워지고, 폰 바꾸기에는 남습니다**(`SEAT_DATA_POLICY.arrivals = 'keep'`).

## 같은 곳 판정(가안)

**이름 정규화가 같고 좌표가 100m 이내**면 같은 곳입니다(`SAME_PLACE_METERS`, 정책서에 값이 없어 정한 가안).

- 이름 정규화: 앞뒤 공백 제거, 안쪽 연속 공백을 하나로, 대소문자 무시, 유니코드 NFC. 띄어쓰기 자체가 다르면(`육전집` ≠ `육전 집`) 다른 이름입니다.
- 거리는 하버사인(미터)이고 100m 정확히는 같은 곳입니다. 후보가 여럿이면 가장 가까운 곳으로 합칩니다.
- 이름이 같아도 100m를 넘으면 다른 곳이고(체인점), 좌표가 같아도 이름이 다르면 다른 곳입니다.
- 합쳐질 때 처음 저장한 이름·좌표를 유지합니다(좌표가 떠돌지 않게). 주소는 처음에 없었으면 나중 값으로 채웁니다.

## API

오류 본문은 `{ error, reason? }`입니다. **새 API에는 옛 차 앱 호환 읽기(`legacyDriverFallback`)를 적용하지 않습니다**: 자리를 정하는 가드는 `seatScope.ts`의 `placeRead`·`placeWrite`(J3의 장소 API와 같은 것)입니다.

| 식별 | 자리 |
| --- | --- |
| 폰 토큰 | 그 자리 |
| 차 토큰 + `driver=<seatId>` | 그 차의 그 자리(`driver` 없음 **400** `driver-required`, 남의 자리 **403**, 모르는 토큰 **401**) |
| 기기 id만 | 그 기기의 연결 전 버킷(읽기만 하고 만들지 않음, 도착 횟수는 늘 비어 있음) |
| 식별 없음 | 서버에 자리 있는 차가 **하나도 없을 때만** 기본 자리(데모·E2E), 그 밖에는 저장하지 않는 빈 범위 |

### `POST /arrivals` (차)

본문(모르는 키는 400): `{ scheduleId?: string, place: { name, lat, lng, address? }, at?: ISO8601 }`

- `place.name`은 앞뒤 공백을 지우고 1~100자, `address`는 200자 이하(비면 `null`), `lat` −90~90·`lng` −180~180(숫자). `scheduleId`는 1~100자.
- `at`(오프셋 있는 ISO8601)은 마지막 날짜를 정하는 데만 쓰고 저장하지 않습니다. 없으면 서버 시각. **서버 시각 기준 3일 전 ~ 10분 뒤**(`ARRIVAL_PAST_LIMIT_MS`·`ARRIVAL_FUTURE_SKEW_MS`, 가안) 밖이면 400 `at-out-of-range`. 마지막 날짜는 뒤로 가지 않습니다(더 이른 `at`이 와도 유지).
- 응답 200 `{ counted: boolean, place: { id, name, address, lat, lng, count, lastDate } | null }`.
- **멱등**: `scheduleId`가 있으면 **그 일정 id의 도착은 (기억이 살아 있는 동안) `at`의 날짜가 달라도 한 번만 셉니다.** 일정 id는 그날의 일정을 가리키기 때문입니다(폰이 보내는 일정 id는 `<캘린더 일정 id>@<시작 시각>`이라 반복 일정도 날짜별로 다른 id입니다). 다시 오면 `counted: false`와 처음 센 장소(그 사이 폰에서 지웠으면 `place: null`)를 주고 횟수를 올리지 않습니다(일정 장소가 바뀌어도, 폰 바꾸기 뒤에도 마찬가지). 기억이 잊힌 뒤(처음 센 날짜가 4일 넘게 지난 뒤)에 같은 id가 다시 오면 새 도착으로 셉니다. `scheduleId`가 없으면 부를 때마다 셉니다(일정이 아닌 장소, 차가 한 번만 부를 책임).
- **차 쪽 계약(재시도)**: 차는 도착을 보낼 때 **처음 정한 `at`을 그대로** 두고, 실패해 다시 보낼 때도 **같은 `at`(과 같은 `scheduleId`)을 보냅니다**(`at`을 지금 시각으로 바꾸지 않음). `at`은 서버 시각 기준 3일 전~10분 뒤만 받으므로(`ARRIVAL_PAST_LIMIT_MS`) 오프라인에서 모았다 보내는 것은 3일 안에 보내야 하고, 그 범위 안에서는 기억이 `at`보다 먼저 사라지지 않아 재시도가 중복으로 세어지지 않습니다. `at`을 3일보다 더 과거로 보내면 400 `at-out-of-range`입니다.
- 차 토큰만 받습니다: 폰 토큰은 **403**, 기기 id만·식별 없음(자리 있는 서버)은 **401**이고 연결 전 버킷을 만들지 않습니다.
- 상한: 자리당 장소 100곳(`MAX_ARRIVAL_PLACES`, 가안). 넘으면 **자주 가는 곳 기준(3회 초과)을 넘지 않은 곳 중에서 가장 오래 안 간 곳**(마지막 날짜가 가장 이른 곳, 같으면 횟수가 적은 곳, 같으면 먼저 만든 곳)부터 지우고 새 곳을 넣습니다. 기준을 넘은 곳은 한 번만 간 곳보다 **나중에** 밀려나고, 모든 곳이 기준을 넘었을 때만 그중 가장 오래 안 간 곳이 밀려납니다. 이미 있는 곳을 다시 세면 마지막 날짜가 갱신돼 밀려나지 않습니다.
- 본문 64KB 초과는 413.

### `GET /places/frequent` (차)

자주 가는 곳 후보. 선택 쿼리 `lat`·`lng`(둘 다)가 있으면 집 반경 안일 때 집을 뺍니다(하나만 오거나 숫자·범위가 틀리면 400).

응답 200 `{ candidates: [{ kind, source, name, address, lat, lng, arrivalCount }], threshold: 3, homeExcluded: boolean }`

- 출처 ①: 폰 앱에서 등록한 집·회사·단골(`kind` `home`·`work`·`other`, 기존 `favorites`), ②: 도착 횟수가 **3회를 넘은**(4회부터, `FREQUENT_ARRIVALS_OVER`, 가안) 장소(`kind: 'other'`, `source: 'arrivals'`). 등록한 곳이 도착 횟수도 가지면 같은 곳으로 합쳐 한 번만 나오고(`source: 'both'`, 등록한 이름·종류를 유지, `arrivalCount`는 합친 횟수) 센 적 없는 등록한 곳은 `arrivalCount: 0`·`source: 'favorite'`입니다.
- **정렬**: 도착 횟수가 3회를 넘은 곳을 **횟수 많은 순**(같으면 마지막 날짜가 가까운 순, 같으면 등록한 순서)으로 앞에 두고(**1순위는 도착 횟수가 가장 많은 곳**), 그 뒤에 나머지 등록한 곳을 집 → 회사 → 추가한 순서로 둡니다. 기준을 넘은 곳이 없으면 결과는 등록한 곳의 기존 순서 그대로입니다. 3회 이하의 도착 횟수는 순서에 영향을 주지 않습니다.
- **집 제외**: 요청 위치가 집(`kind: 'home'`) 반경 300m(`HOME_RADIUS_METERS`, 정책서 12장 '집 반경', 가안) 이내(300m 정확히는 이내)면 집을 뺍니다(`homeExcluded: true`). 다른 곳은 현재 위치와 가까워도 빼지 않습니다.
- **내비 즐겨찾기·최근 목적지(정책서 8장 둘째 출처)는 차가 NaviHelper에서 받아 이 목록과 합칩니다**(서버는 모릅니다). 합칠 때 같은 곳 판정은 위 규칙을 쓰면 서버 결과와 일관됩니다.
- 폰 토큰으로도 읽을 수 있고(그 자리), 기기 id만·식별 없음(자리 있는 서버)은 빈 후보입니다.

### 폰용: 도착 횟수 보기·지우기

- `GET /places/arrivals` → `{ arrivals: [{ id, name, address, lat, lng, count, lastDate, qualifies }], threshold: 3 }`. 횟수 많은 순이고 `qualifies`는 후보 기준(3회 초과)을 넘었는지입니다.
- `DELETE /places/arrivals/:id` → `{ removed: true, id }`, 없는 id(다른 자리의 id 포함)는 404. 지우면 후보에서도 빠집니다. 정책서 11장 '사용자가 지울 때까지'를 위한 API이고 화면은 다른 묶음입니다.
- 폰 토큰·기기 id(빈 목록, 버킷을 만들지 않음)·기본 자리만 쓰고 **차 토큰은 403**입니다(폰에서만 보고 지움). 모르는 폰 토큰은 401(폰이 토큰을 버리고 다시 보냄).

## `GET /schedules/today`의 `favorites`

차 앱이 지금 쓰는 응답에도 같은 정렬 결과가 반영됩니다(`schedules.ts`가 `rankCandidates`를 씀). **단, 명시 식별로 자리가 정해졌을 때만**입니다: 폰 토큰, 또는 차 토큰 + `driver=<seatId>`(`SeatScope.explicit`). **옛 차 앱 호환 읽기(식별 없는 읽기·차 토큰만 있고 `driver` 없음)와 기본 자리(데모·E2E·픽스처)에서는 도착 횟수를 섞지 않고 등록한 집·회사·단골만 줍니다.** 지금 차 앱은 도착을 보내지 않고 `driver`도 보내지 않으므로 동작이 달라지지 않으며(데모를 반복해도 후보 순서가 바뀌지 않음), 옛 호환 범위의 응답에 다른 자리·다른 폰의 도착 장소가 새는 길도 없습니다. 차 앱이 `driver`를 보내기 시작하면(옛 호환 종료) 그 요청부터 도착 횟수가 반영됩니다. **호환 근거**(차 앱 `ScheduleParser`·`BoardingDecider`·`Phrases`를 읽고 확인):

- 항목 모양은 그대로입니다: `{ kind, name, address, lat, lng }`(`arrivalCount`·`source` 같은 새 필드는 `favorites`에 넣지 않고 `/places/frequent`에만 둡니다). `address`는 문자열이고, 도착 횟수로만 올라온 곳의 주소를 모르면 빈 문자열입니다(차 앱은 `address`를 문자열로 읽음). 도착 횟수로 올라온 곳은 `kind: 'other'`라 차 앱의 `FavoriteKind.OTHER`(장소 이름이 후보 이름, 주소가 설명)로 읽힙니다.
- **기준(3회)을 넘은 곳이 없으면 응답이 도착 횟수 기능 이전과 바이트 단위로 같습니다**(집 → 회사 → 추가한 순서). 기본 자리(픽스처·데모·차량 E2E)는 `POST /arrivals`가 없으면 그대로이고, 기존 서버·차량 테스트가 읽는 응답은 변하지 않습니다(`server/test/arrivals.test.ts`가 비교).
- 넘은 곳이 생기면 그곳이 앞에 오므로 차의 후보 표시(최대 3개, 1번 후보가 주 버튼)가 달라집니다 — **정책서가 원하는 동작**(1순위 = 최다 도착)입니다. 다만 `/schedules/today`는 현재 위치를 모르므로 **집을 빼지 못합니다**(지금 집이면 집을 빼는 일은 차가 현재 위치로 `/places/frequent?lat=&lng=`를 부르거나 자기 위치로 걸러야 합니다).
- 차 앱의 일정 응답 사본(그날 저장)은 받은 순서를 그대로 씁니다.
- 기본 자리에서 `POST /arrivals`로 4회 이상 쌓아도 `/schedules/today` 응답(픽스처 경로)은 변하지 않습니다(`server/test/arrivals.test.ts`). 반면 새 API `GET /places/frequent`는 기본 자리에서도 도착 횟수를 보여 줍니다(식별 없는 읽기가 실제 자리를 읽는 길은 없고, 기본 자리는 자리 있는 차가 없는 서버에서만 쓰임).

## 차 쪽·폰 쪽이 이어 붙일 것

- 차: 도착을 기록하는 곳(`DriveSession.arrive`의 내비 도착·위치 도착)에서 `POST /arrivals`(`Authorization: Bearer <차 토큰>`, `?driver=<자리 id>`)를 부릅니다. 본문의 `scheduleId`는 도착한 일정 id, `place`는 일정 장소(이름·좌표, 주소가 있으면)입니다. 같은 일정은 서버가 중복을 막으므로 재시도해도 안전합니다. 일정이 아닌 장소(집 하차 등)를 센다면 `scheduleId` 없이 부르되 차가 한 번만 부릅니다. 후보는 `GET /places/frequent?driver=&lat=&lng=`로 받거나 기존 `GET /schedules/today`의 `favorites`를 그대로 씁니다.
- **데모·E2E 초기화**: 기본 자리(데모 경로)의 도착 횟수를 비우려면 **같은 기기에서 `DELETE /events`**를 부릅니다(기존 개발용 초기화. 기본 자리를 비울 때만 도착 횟수·일정 id 기억도 함께 비움, 실제 자리의 도착 횟수는 건드리지 않음). 차 쪽 묶음의 데모·E2E 초기화 스크립트가 이 호출을 씁니다.
- 폰: 설정/장소 화면이 `GET /places/arrivals`로 보여 주고 `DELETE /places/arrivals/:id`로 지웁니다(`api` Hono RPC 클라이언트로 부르면 됩니다).

## 정책서와 다른 점·가안

- 같은 곳 100m, 후보 3회 초과, 집 반경 300m, 장소 100곳 상한, `at` 범위(3일 전~10분 뒤), 일정 id 기억 4일·500개는 모두 **가안**입니다(정책서에 값이 있는 것은 3회·300m뿐이고 그것도 12장에서 가안).
- 도착을 센 장소가 후보에 올라오는 것은 **횟수 기준뿐**이라 오래전에 자주 가던 곳도 횟수가 남아 있으면 앞에 옵니다(최근성은 동률일 때만 봅니다). 최근 N일만 세는 방식은 저장 항목(장소·횟수·마지막 날짜)을 늘려야 해서 쓰지 않았습니다.
- 도착 횟수로 올라온 곳은 도착 때 차가 보낸 이름·좌표를 그대로 씁니다(서버가 장소 검색 결과나 목 장소로 풀지 않음). 같은 곳이 이름만 달라(`집` vs `예시 아파트 101동`) 따로 세어질 수 있고, 등록한 집과 합쳐지려면 차가 등록한 이름으로 보내야 합니다.
- 메모리 저장입니다. 서버를 다시 켜면 횟수가 사라집니다(영속화하면 자리와 함께 저장).
- **확인 필요(정책서와 다른 점)**: 30일 동안 일정을 보내지 않은 폰(캘린더 권한 꺼짐 등)은 정기 정리(`prune-silent-seats`)로 **자리와 기억(도착 횟수 포함)이 함께 지워집니다**. 정책서 10.9·12장은 '30일 무소식 자리 정리'만 말하고, 권한을 껐을 뿐 폰을 계속 쓰는 사용자의 기억까지 지우는 것이 맞는지는 확인이 필요합니다(지우지 않고 기억만 남기는 방향도 있음). 서버 시계 이상에 대비해 한 번에 지울 자리가 전체의 절반을 넘고 4개 이상이면 그 실행은 건너뜁니다(`docs/pairing.md`).
