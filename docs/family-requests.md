# 가족 묶기와 가족 요청 (서버)

정책서 10.10 '가족 요청'·11장(가족, 가족 요청, 주행 상태, API 표, 정기 작업)·12장('들르기 묶는 거리', '픽업 곧 도착 알림')·13장('가족 초대 코드 유효 시간·인원 한도')의 **서버 쪽** 구현입니다(묶음 J10a).
폰 가족 탭(묶기·요청 만들기·상태·공유 화면, 묶음 J10b)은 이 계약을 부르는 쪽으로 **구현했습니다**(아래 '폰 가족 탭 화면과 저장 방식'). 차 쪽(요청을 일정과 같은 판단 순서에 넣기, 전달·수락·도착 신호 보내기)은 아직 다른 묶음입니다. 서버는 전달과 기억만 하고 판단은 하지 않습니다.

코드: `server/src/family/`(`groups.ts` 가족·구성원·구성원 비밀값·초대·공유, `requests.ts` 검증·상태 전이 표, `service.ts` 요청·알림·주행 상태, `guard.ts` 호출자 정하기, `jobs.ts` 정기 작업, `phrases.ts` 알림 문구, `limits.ts` 기준값)와 `server/src/routes/familyGroup.ts`·`routes/requests.ts`. 테스트는 `server/test/family-groups.test.ts`·`family-requests.test.ts`·`family-security.test.ts`(리뷰 반려 지적 재현: 비밀값 신분, '우리 차' 요청의 유효성·삭제, 가족 수 상한 남용, 알림 정리).

## 데이터 모델 (모두 메모리, 서버를 다시 켜면 사라짐)

| 데이터 | 내용 | 보관 |
| --- | --- | --- |
| 가족 | 가족 id, 구성원(들어온 순서), 초대 코드(하나, 24시간) | 구성원이 모두 나갈 때까지 |
| 구성원 | 구성원 id(`memberId`, 공개해도 되는 난수), 부르는 이름, **구성원 비밀값**(256비트 난수, 서버 안에서만), 묶인 폰 자리(`seatId`+그 자리의 차, 없을 수 있음), 마지막으로 쓴 시각 | 가족에서 나갈 때까지(30일 비활동이면 정리) |
| 도착 예정 공유 | 구성원별로 '내 도착 예정을 보여 주는 가족' 집합. 기본 꺼짐 | 가족에서 나갈 때까지(나간 사람과 얽힌 설정은 둘 다 지움) |
| 가족 요청 | 카테고리·카테고리별 항목·한 줄 메모·날짜·상태, 보낸 구성원, 받는 구성원 또는 '우리 차'(서버 안의 차 id), 만든 시각, 5분 전 알림을 보냈는가(`etaSoon`). **바뀐 시각(전이 시각)은 저장하지 않음** | **그날(서울 날짜)이 끝날 때까지**(완료·거절도 같음), '우리 차'는 그 차에 가족 자리가 남아 있는 동안만 |
| 주행 상태 | 자리별 주행 중/정차와 바뀐 시각. **위치는 없음** | 마지막 값만, 그날까지 |
| '우리 차' 가리킴값(`carRef`) | 가족 id + 차 id → 불투명한 값 | 그 차에 가족 자리가 있는 동안(없어지면 지움) |

저장하지 않는 것: 요청이 바뀐 시각, 위치·경로, 이유·답장. 도착 예정 시각(`etaAt`)은 **요청에는 남기지 않고** 5분 전 알림 `data`로만 전달하며, 그 알림이 보낸 사람 알림함에 **최대 1시간**(`ETA_NOTIFICATION_TTL_MS`, 폰이 `ack`하면 즉시 삭제) 머뭅니다(아래 알림 절).

- **가족은 차와 따로 묶입니다.** 가족을 만들거나 들어가는 데 차 연결이 필요 없고, 차 연결을 끊거나 차곡을 초기화해도 가족(과 구성원)은 그대로입니다. 다만 '우리 차' 요청은 그 차에 가족 자리가 남아 있을 때만 유효합니다(아래 전달 규칙).
- **구성원 신분 = 구성원 비밀값**(리뷰 반려 지적의 근본 해결): 가족을 만들거나(`POST /family/invite`) 참여할 때(`POST /family/join`) 서버가 구성원 비밀값(`memberToken`, 64자 16진수)을 **응답에 한 번만** 싣습니다. 폰이 `expo-secure-store`에 저장하고(폰 묶음의 몫) 이후 가족·요청 호출마다 `X-Chagok-Member: <비밀값>` 헤더로 보냅니다. 서버는 비밀값을 로그·다른 응답에 내보내지 않습니다(`GET /family`·`GET /requests`·알림에도 없음). **기기 id(`X-Chagok-Device`)는 가족 신원으로 쓰지 않고 읽지도 않습니다**(남의 기기 id를 알아도 구성원을 가로챌 수 없고, 헤더에 임의 값을 붙여 서버 상태를 늘릴 수 없음). 연결 전 폰도 비밀값으로 가족 기능을 씁니다.
- **자리와 구성원을 묶는 규칙**: 폰 신원은 ① 구성원 비밀값, ② 이미 구성원에게 묶인 자리의 폰 토큰, 둘 중 하나입니다. 자리를 구성원에게 묶는 것은 **비밀값과 폰 토큰이 같은 요청에 함께 온 경우**(본인이 둘 다 가졌음의 증명)뿐이고, 그 자리가 아직 아무에게도 안 묶였을 때만입니다(다른 구성원에게 묶인 자리는 건드리지 않고 비밀값 쪽이 이김). 구성원당 자리는 하나라 다른 자리를 같이 보내면 그 자리로 옮겨 갑니다(폰을 다른 차에 다시 연결한 경우). 가족을 만들거나 참여하는 요청에 폰 토큰을 같이 보내면 그 자리가 새 구성원에게 바로 묶입니다. 그 밖의 경우는 연결 뒤 첫 가족 호출에 두 헤더를 함께 보내면 됩니다.
- **끊기·초기화·폰 바꾸기**: 연결 끊기·차곡 초기화·자리 정리로 자리가 사라지면 묶음만 풀리고 **구성원은 비밀값으로 가족에 남습니다**(옛 폰 토큰은 401). 폰 바꾸기(replace)는 자리가 그대로라 구성원도 이어지고, 새 폰은 비밀값 없이 폰 토큰만으로 같은 구성원입니다. **비밀값을 잃은 구성원(앱 삭제)은 새로 참여해야 하고**(새 구성원·새 비밀값) 옛 구성원은 30일 비활동 정리를 기다립니다. 가족을 나가거나 정리된 구성원의 비밀값은 401 `unknown-member`가 되므로 폰은 저장해 둔 비밀값을 지웁니다.
- **남용 방지**(식별 없이도 가족을 만들 수 있으므로): 한 요청 주소가 10분에 가족 10개·**하루(24시간)에 20개**까지 만들 수 있고(`MAX_FAMILY_CREATES_PER_SOURCE`·`MAX_FAMILY_CREATES_PER_SOURCE_PER_DAY`, 넘으면 429 `rate-limited`, 기록을 가진 주소는 1000개까지이고 표가 차면 새 주소도 막음), 구성원 1명뿐이고 요청이 없는 가족은 그 구성원이 마지막으로 쓴 지 **24시간 뒤 정리**됩니다(`SOLO_FAMILY_TTL_MS`, 가안). 서버가 아는 가족이 300개(`MAX_FAMILIES`)에 닿으면 **혼자뿐이고 요청이 없는 가장 오래 쓰지 않은 가족부터 밀어내고**(그 구성원의 비밀값은 401이 됨) 새 가족을 만들며, 밀어낼 가족이 없을 때만 429 `too-many-families`입니다. 한 가족 6명, 보낸 사람 한 명의 진행 중 요청 30개·가족 하나 100개(429 `too-many-requests`). **구성원은 가족 API(폰의 호출, 또는 차가 그 자리로 부른 호출)를 30일 쓰지 않으면** 연결 여부와 관계없이 정기 작업이 가족에서 내보냅니다(`MEMBER_INACTIVE_TTL_MS`, 가안, 연결 전 일정 버킷의 7일과 따로).

## 호출자 정하기 (`family/guard.ts`)

J1의 자리 규칙(`docs/pairing.md`)을 따르되, J3의 새 장소 API 가드(`placeRead`·`placeWrite`)와 같은 엄격한 방식입니다. **옛 차 앱 호환 읽기(`legacyDriverFallback`)와 기본 자리를 적용하지 않습니다.**

| 호출자 | 식별 | 결과 |
| --- | --- | --- |
| 폰 | `X-Chagok-Member`(구성원 비밀값) | 그 구성원(폰 토큰이 같이 오면 자리를 묶음, 위 규칙) |
| 폰 | 폰 토큰만 | 그 자리에 묶인 구성원(묶인 구성원이 없으면 가족 없음: `GET /family`는 `family: null`, 만들기·조회는 409·404) |
| 폰 | 식별 없음 | **401**(`POST /family/invite`·`/join`만 예외: 식별 없이 부르면 새 구성원이 됨) |
| 폰 | 모르는 비밀값(나간·정리된 구성원) | 401 `unknown-member` |
| 폰 | 이상한 비밀값 모양(32~128자의 영문·숫자·`-`·`_` 아님) | 400 `bad-member` |
| 폰 | 모르는 폰 토큰·이상한 Authorization 형식 | 401(폰이 토큰을 버리고 비밀값만으로 다시 보냄) |
| 폰 | 기기 id만(`X-Chagok-Device`) | **식별 없음과 같음**(기기 id는 읽지 않음) |
| 차 | 차 토큰 + `driver=<자리 id>` | 그 차의 그 자리 |
| 차 | 차 토큰만(`driver` 없음) | **400 `driver-required`**(J3와 같은 문구·상태. '지난번 고른 자리'로 고르지 않음) |
| 차 | `driver`가 빈 값이거나 그 차의 자리가 아님 | 403 |
| 차 | 토큰 없음·모르는 토큰·폰 토큰 | 401 |

`driver`는 같은 이름의 값이 여럿이면 **첫 값**을 쓰고, 읽는 함수(`seatScope.ts`의 `driverOf`)를 자리 정하기 가드와 가족 가드가 같이 씁니다(둘의 판정이 어긋나지 않음).
`GET /requests`는 폰과 차가 같은 주소를 쓰므로 차 토큰이면 차, 아니면 폰으로 봅니다. 차 쪽 경로(`PATCH`·`eta`·`/drive-state`)는 차 토큰만 받습니다.

## API

오류 본문은 `{ error, reason? }`입니다. 폰은 `X-Chagok-Member: <구성원 비밀값>`과 `Authorization: Bearer <폰 토큰>`(연결돼 있으면), 차는 `Authorization: Bearer <차 토큰>`과 `?driver=<자리 id>`입니다.

### 가족 (폰)

| 호출 | 하는 일 | 오류 |
| --- | --- | --- |
| `GET /family` | 식별이 필요합니다(비밀값 또는 묶인 폰 토큰). `{ family: null }`(폰 토큰만 있고 구성원에게 묶이지 않음) 또는 `{ family: { familyId, createdAt, maxMembers, invite: { code, expiresAt } \| null, me: { memberId, name }, members: [{ memberId, name, isMe, connected, shareWithThem, sharesWithMe }], cars: [{ carRef, memberIds }] } }`. `connected`는 그 사람 폰이 어느 차에 연결돼 있는가, `shareWithThem`은 내가 그에게 도착 예정을 보여 주는가, `sharesWithMe`는 그가 나에게 보여 주는가. `cars`는 '우리 차'로 고를 수 있는 차(가족 폰이 연결된 차)와 그 차에 연결된 구성원. `carRef`는 불투명한 값이고 서버 안의 차 id는 나가지 않음 | |
| `POST /family/invite` `{ name? }` | 초대 코드 만들기. **식별 없이 부르면** 가족을 만들고 부른 사람이 첫 구성원(`name`은 부르는 이름, 생략하면 '가족', 20자)이 되며 **`memberToken`(구성원 비밀값)을 이 응답에서 한 번만** 줍니다(폰 토큰을 같이 보내면 그 자리가 바로 묶임). 이미 구성원(비밀값 또는 묶인 폰 토큰)이면 새 코드로 바꿈(이전 코드는 즉시 무효, `memberToken`은 null). → `{ code, expiresAt, expiresInSeconds, created, memberToken: string \| null, family }` | 409 `family-full`, 429 `rate-limited`·`too-many-families` |
| `POST /family/join` `{ code, name? }` | 코드로 참여. 코드는 `ABCD-EFGH`(대소문자·공백·하이픈 무시). 새 구성원이 되며 **`memberToken`을 이 응답에서 한 번만** 줍니다. → `{ memberToken, family }` | 404 `invalid`(없는·만료된 코드, 같은 응답), 409 `already-in-family`(어느 가족이든 이미 구성원이면, 같은 가족에 다시 넣어도), 409 `family-full`, 429 `locked`(+`Retry-After`) |
| `PUT /family/me` `{ name }` | 내 부르는 이름 바꾸기(한 가족 안에서 겹치면 ` 2`) | 404 `not-in-family` |
| `DELETE /family/me` | 가족 나가기: **내가 보낸·받은 요청과 공유 설정(내가 켠 것·나에게 켠 것)을 지움**. 마지막 구성원이면 가족도 사라짐. 나간 구성원의 비밀값은 이후 401. 이 구성원이 보낸·받은 요청의 `family-status` 알림도 알림함에서 지움. 그 차에 가족 자리가 안 남으면 그 차로 보낸 '우리 차' 요청도 지움. → `{ left: true }` | 404 `not-in-family`(폰 토큰만 있고 묶인 구성원이 없을 때) |
| `PUT /family/share` `{ memberId, enabled }` | **내가** 가족 한 사람에게 내 도착 예정(약속·픽업 요청의 시각과 주행 중 여부)을 보여 줄지. 기본 꺼짐. → `{ memberId, enabled }` | 400 `self`, 404 `unknown-member`·`not-in-family` |

- **초대 코드**: 8자리(헷갈리는 0·1·I·L·O를 뺀 31글자, 8.5×10¹¹가지). 정책서 13장 미결이라 **가안으로 24시간·가족 6명**(`FAMILY_INVITE_TTL_MS`·`MAX_FAMILY_MEMBERS`)이고 상수 한 곳(`family/limits.ts`)입니다. 한 가족에 코드는 하나이고 **만료 전까지 인원이 찰 때까지 여럿이 쓸 수 있습니다**(가족이 여러 명이라 한 번만 쓰는 코드면 사람 수만큼 만들어야 함. 코드가 새면 24시간 동안 들어올 수 있으므로 누구든 새 코드를 만들어 바꿀 수 있음). 차 연결 코드(5분)와 달리 24시간 살아 있어 6자리 숫자로는 서버 전체 시도 제한(분당 120번)으로도 무차별 대입을 막기 어려우므로 8글자로 늘렸습니다.
- **시도 제한**: 차–폰 연결 코드(`seats.ts` claim)와 같은 방식·같은 기준값입니다(`family/attempts.ts`): 틀린 코드를 한 요청 주소가 60초에 5번 넣으면 그 주소를 60초 막고(잠긴 동안은 맞는 코드도 429, 잠금을 늘리지 않음), 실패 기록 표가 차면(주소 100개) 새 주소를 잠금으로 보고(fail-closed), 서버 전체 120번/60초면 모두 막고, 잠금은 60초를 넘지 않습니다. 맞히면 그 주소의 실패 횟수를 지웁니다. 요청 주소는 `createApp({ clientAddress })`입니다(프록시 뒤에서는 바꿔야 함).

### 요청

| 호출 | 부르는 쪽 | 하는 일 |
| --- | --- | --- |
| `POST /requests` | 폰 | 요청 만들기(아래 본문). 상태는 `sent`(보냄). → `{ request }`(보낸 사람 모양) |
| `GET /requests?date=` | 폰 | `{ sent, received, serverTime }`. 보낸 것·받은 것(사람으로 받은 것, 내 폰이 연결된 차가 '우리 차'로 받은 것)과 상태, 최근에 만든 것부터. `date`(`YYYY-MM-DD`)를 주면 그날만. 가족이 없으면 둘 다 빈 배열 |
| `GET /requests?date=&driver=` | 차 | `{ driver, date, requests, serverTime }`. 그 자리로 온 요청과 이 차의 '우리 차'로 온 요청 중 그날(기본 오늘) **아직 끝나지 않은 것**(`sent`·`delivered`·`accepted`)만. `driver`가 누구든 '우리 차' 요청은 들어 있음 |
| `PATCH /requests/:id` `{ status }` | 차 | 상태 바꾸기: `delivered`·`accepted`·`declined`·`completed`. → `{ request, changed }`. 바뀌면 보낸 사람 알림함에 `family-status` |
| `POST /requests/:id/eta` `{ stage, etaAt? }` | 차 | 도착 5분 전(`soon`)·도착(`arrived`). → `{ notified }` |
| `POST /drive-state` `{ driving }` | 차 | 이 자리의 주행 시작·멈춤. → `{ seatId, driving, changedAt }` |

**`POST /requests` 본문**(항목은 카테고리별로 정해져 있고 그 밖의 항목은 400. 공통: `category`, `recipient`, `memo?`):

| `category` | 항목 | 날짜 |
| --- | --- | --- |
| `care` 채비 | `item`(물건, 60자), `timing`(`take-along` 가져갈 때 \| `bring-back` 가져올 때), `date?` | `date`(기본 오늘) |
| `stop` 들르기 | `place`, `item`(살 것·찾을 것), `deadline`(`{ type: 'today' }` 오늘 중 \| `{ type: 'by', time: 'HH:MM' }`), `date?` | `date`(기본 오늘) |
| `appointment` 약속 가기 | `at`(오프셋 있는 ISO8601), `place`, `companions?`(함께 가는 사람 이름, 10명·각 40자) | `at`의 서울 날짜 |
| `ride` 데려다주기·픽업 | `who`(누구를, 40자), `pickup`(어디서), `dropoff`(어디로), `at` | `at`의 서울 날짜 |

- `recipient`: `{ memberId }`(가족 한 사람) 또는 `{ carRef }`('우리 차', `GET /family`의 `cars`에서 고름). 자기 자신·다른 가족·가족 폰이 연결되지 않은 차는 400(`self`·`unknown-recipient`·`unknown-car`). 가족이 없으면 409 `not-in-family`.
- `place`·`pickup`·`dropoff`: `{ text, lat?, lng? }`(글자 100자 + 좌표는 둘 다 있거나 둘 다 없음). **장소 해석은 서버가 하지 않고 받은 대로 담습니다**(해석은 차·다른 묶음).
- `memo`: 한 줄(줄바꿈·연속 공백은 공백 하나로), 100자 이하, 비면 null. 차가 30자 이하면 읽고 길면 '메모가 있어요'만 말하는 것은 차의 몫.
- 날짜는 **오늘·내일(서울)만** 받습니다(일정과 같은 범위, 가안). `at`은 UTC ISO로 정규화해 돌려줍니다.
- `at`(약속 가기·데려다주기·픽업)이 **이미 지난 시각이면 400**입니다(`PAST_AT_LEEWAY_MS` 10분까지의 지난 시각은 여유로 받음).
- 응답 필드(보낸 사람 모양): `id, category, <카테고리 항목>, memo, date, status, createdAt, from: { memberId, name }, to: { kind: 'member', memberId, name } | { kind: 'car', carRef }, reachable, drivingNow, etaStage`. **바뀐 시각(`updatedAt` 등 정밀한 전이 시각)은 주지 않습니다**(만든 시각 `createdAt`만, 상태는 코드뿐). 받은 사람 모양(`received`)은 `drivingNow`·`etaStage`가 없습니다. `reachable`은 받는 사람에게 닿을 곳이 있는가(사람: 폰이 어느 차에 연결돼 있는가, 차: 그 차에 이 가족의 자리가 있는가) — 거짓이면 그 사람 폰 앱에만 보입니다.
- 차 모양(`GET /requests?driver=`): `id, category, <카테고리 항목>, memo, date, status, createdAt, from: { memberId, name }, via: 'seat' | 'car'`. **`createdAt`은 서버가 요청을 받은 시각**이라 차가 '주행 중에 온 요청은 말하지 않고 다음 탑승에 전한다'(정책서 6장)를 자기 주행 상태와 이 시각으로 판단할 수 있습니다.

## 상태 전이 표

상태 코드: `sent` 보냄 → `delivered` 전달 → `accepted` 수락 \| `declined` 거절 → `completed` 완료. **문구는 클라이언트(폰) 몫**이고 서버는 코드만 줍니다(알림 문구만 서버가 만듦, 아래).

| 카테고리 | `sent` | `delivered` | `accepted` | `declined` | `completed` |
| --- | --- | --- | --- | --- | --- |
| 채비 | → delivered | → completed | (도달 안 함) | (도달 안 함) | 끝 |
| 들르기 · 약속 가기 · 데려다주기·픽업 | → delivered | → accepted, declined, completed | → completed | 끝 | 끝 |

- 차가 PATCH로 바꾸는 값은 `delivered`·`accepted`·`declined`·`completed` 넷이고, `sent`는 만들 때의 상태라 차가 되돌릴 수 없습니다(**400**: 본문 모양·모르는 상태 값·`sent`).
- **표에 없는 전이는 409 `invalid-transition`**(본문에 `from`·`to`): 채비의 수락·거절, 보냄에서 바로 수락·완료(먼저 전달), 끝난 요청(거절·완료)의 모든 변경, 수락 후 거절 등.
- **같은 상태로 다시 보내면 200 + `changed: false`**이고 아무것도 하지 않으며 알림도 없습니다(차의 재시도 안전).
- 채비는 묻지 않고 말만 해서 수락·거절이 없습니다. 나머지는 `delivered → completed`도 됩니다(그 장소에 도착했는데 '응'을 안 했거나 무응답이었던 경우).
- 보낸 사람 폰 문구(정책서 10.10 표 — 폰이 이 표로 정함): 채비 '전달했어요'(`delivered`), 들르기 '수락했어요'(`accepted`) → '들렀어요'(`completed`), 약속 '출발했어요'(`accepted`) → '도착했어요'(`completed`), 픽업 '수락했어요'(`accepted`) → '곧 도착해요'(`etaStage: 'soon'`) → '도착했어요'(`completed`), 거절은 '이번엔 어려워요'(`declined`)만(이유·답장 없음). 보냄 문구는 `drivingNow`가 참이면 '운전 중이라 다음 정차 때 전해요', 아니면 '차에 타면 전해요'.
- 접근: 차는 **그 자리로 온 요청, 또는 이 차의 '우리 차' 요청**만 PATCH·eta 할 수 있습니다. 그 밖(받는 사람이 아닌 차·같은 차의 다른 자리·다른 가족의 요청)은 없는 요청과 같은 **404 `not-found`**입니다.

## 전달 규칙

- **사람에게 보낸 요청**: 그 사람 폰이 연결된 운전자 자리로 갑니다. 차는 `GET /requests?driver=<그 자리>`로 받고, 같은 차의 다른 자리·다른 차에는 안 나옵니다. 연결은 조회 때마다 보므로 나중에 폰이 차에 연결하면 그때부터 그 자리로 갑니다. '그 자리가 지금 운전자로 정해졌을 때만 전한다'는 운전자 판단(5장 2번)이라 차의 몫입니다.
- **받는 사람 폰이 어느 차에도 연결되지 않았으면**: 요청은 그 사람 폰 앱(`GET /requests`의 `received`)에만 보이고 차 조회에는 안 나옵니다(`reachable: false`).
- **'우리 차'**: 가족 폰이 연결된 차 중에서 고르며(`GET /family`의 `cars`, 가리킴값은 **가족마다 다름**), 그 차의 어느 자리로 조회해도 들어 있어 그 차에 다음에 타는 운전자가 받습니다. 그 차에 연결된 가족은 '받은 요청'에서 봅니다(보낸 사람 본인은 보낸 쪽에만). **유효 조건**: '우리 차' 요청은 **지금 그 차에 그 가족 구성원의 자리가 하나 이상 있을 때만** 조회·PATCH·eta·`reachable`에서 살아 있습니다(아니면 차에는 404·안 보임). 같은 차에 가족 아닌 동료의 자리가 있어도 가족 자리가 남아 있으면 정책대로 보입니다(그 차에 다음에 타는 운전자). 그 차의 **마지막 가족 자리가 사라지면(연결 끊기·차곡 초기화·30일 자리 정리·구성원의 가족 나가기·구성원이 다른 차로 옮김) 그 차로 보낸 '우리 차' 요청을 지우고** 가리킴값도 지웁니다(옛 가리킴값으로는 새 요청을 못 보냄). 그 차를 초기화한 뒤 낯선 사람이 연결해도 이전 가족의 요청이 넘어가지 않습니다.
- **받는 사람 폰에는 알림을 보내지 않습니다**(오늘·가족 탭에만 보임). 알림은 보낸 사람에게만 갑니다.
- 주행 중에 온 요청을 말하지도 칩에 띄우지도 않는 것은 차의 몫입니다. 서버는 요청마다 `createdAt`을 줍니다.

## 알림 (J7 알림함, `family-status`)

보낸 사람의 자리 알림함(`notifier.notify(seatId, { kind: 'family-status', … })`)에 넣습니다. 차에 연결하지 않은 보낸 사람(묶인 자리가 없는 구성원)은 알림함이 없어 건너뛰고 `GET /requests`로 상태를 봅니다.

- **언제**: PATCH로 상태가 **실제로 바뀔 때** `delivered`·`accepted`·`declined`·`completed`(보내기만으로는 없음). 도착 예정 공유를 켠 경우의 5분 전·도착(`eta`).
- 제목 `"{받는 사람 이름}에게 보낸 {카테고리}"`(`우리 차에 보낸 …`), 본문은 상태 문구(`family/phrases.ts`, 가안): `delivered` '전달했어요', `accepted` 약속 '출발했어요'·그 밖 '수락했어요', `declined` '이번엔 어려워요', `completed` 들르기 '들렀어요'·약속·픽업 '도착했어요'·채비 '챙기라고 전했어요', 5분 전 픽업 '곧 도착해요'·약속 '5분 뒤 도착해요'.
- `data`: `{ requestId, category, status }` + 5분 전·도착이면 `stage: 'soon' | 'arrived'`, 5분 전에 `etaAt`(받은 값, UTC ISO)이 있으면 `etaAt`. 알림에는 만든 시각이 있어(알림 폴링의 `createdAt`) 상태가 바뀐 때를 알 수 있습니다(알림 자체의 성격).
- **보관**: 일반 상태 알림은 알림함 기본값(3일). **도착 예정 알림(5분 전·도착)은 1시간**(`ETA_NOTIFICATION_TTL_MS`, `notify`의 `ttlMs`)만 머물고 폰이 `POST /notifications/ack`로 읽어 가면 즉시 지웁니다(그래서 `etaAt`은 알림함에 길어야 1시간). 알림함은 서버 메모리뿐입니다(FCM을 켜도 서버는 TTL을 FCM에 넘기지 않고, FCM은 기본 꺼짐·미확인).
- **요청이 지워지면 알림도 지웁니다**: 가족 나가기·'우리 차' 자리 없어짐·날짜 지남으로 요청이 지워지면 그 요청 id의 `family-status` 알림을 모든 자리 알림함에서 지웁니다(`notifier.retract`). 중복 억제 키는 남겨 같은 알림이 다시 만들어지지 않습니다. 폰은 `registerTapHandler('family-status', …)`로 `requestId`의 상태 화면을 엽니다.
- 중복 억제 키 `family-status:<요청 id>:<상태|soon|completed>`: 같은 상태는 한 번. 도착(`arrived`)은 완료와 같은 키라 **eta로 도착을 알린 뒤 완료 PATCH가 두 번째 알림을 만들지 않습니다**.

### 도착 예정 공유와 `eta`

- `PUT /family/share`는 **받는 사람(운전하는 사람)이** 보낸 사람 한 명마다 켭니다(기본 꺼짐). 켠 경우에만 진행 중인 **약속 가기·픽업** 요청의 5분 전·도착이 보낸 사람에게 갑니다(도착 예정 정보는 이 두 카테고리에서만 줍니다). 위치·경로는 보내지 않고, **도착 예정 시각은 알림 `data`로 전달만 하며 요청에는 저장하지 않습니다**(알림함에는 위 TTL 동안 남음). 보낸 사람 조회의 `etaStage: 'soon'`은 단계일 뿐 시각이 없습니다.
- `POST /requests/:id/eta`: 약속·픽업만(그 밖은 409 `not-eta-category`), 전달·수락 상태만(보냄·끝난 요청은 409 `not-in-progress` — **요청이 끝나면 공유도 끝남**). 공유가 꺼져 있으면 200 `{ notified: false }`로 아무것도 안 합니다. `soon`에만 `etaAt`을 쓸 수 있습니다. `arrived`는 상태를 바꾸지 않습니다(완료는 PATCH). '우리 차'로 보낸 요청은 받는 사람이 사람이 아니라 공유 설정이 없어 늘 `notified: false`입니다.
- `etaStage`는 공유가 켜져 있고 끝나지 않은 요청에서만 `'soon'`, 공유를 끄면 가려집니다.
- **`drivingNow`**(보낸 사람 조회): **약속 가기·데려다주기·픽업 요청**이고 `sent`이며 받는 사람이 보낸 사람에게 도착 예정 공유를 켰고 그 사람의 자리가 지금 주행 중일 때만 `true`(채비·들르기는 늘 `false`: 정책 10.10 '도착 예정 공유'는 약속·픽업의 도착 예정과 주행 중 여부). 공유를 안 켰으면 주행 중이어도 늘 `false`라 주행 여부가 새지 않습니다. 차에 연결 안 한 받는 사람·'우리 차'는 늘 `false`.
- `POST /drive-state`: 자리별 마지막 값만(바뀔 때만 바뀐 시각을 새로 함), **그날까지**(날짜가 바뀌면 주행 중이 아닌 것으로 봄), 자리가 지워지거나 폰이 바뀌면 지움. 위치 같은 다른 항목은 400. 보낸 사람 폰의 '운전 중이라 다음 정차 때 전해요'에만 씁니다.

## 보관·정기 작업

- 정책서 11장 '완료되거나 날짜가 지나면 삭제'. **날짜가 지난 요청(서울 날짜)은 읽기·쓰기에서 이미 보이지 않고**(자정이 지나면 정기 작업이 아직 안 돌았어도 조회·PATCH가 404), 정기 작업 `family-requests-expire`(`family/jobs.ts`, J7 스케줄러 `scheduler.register`, `server/src/index.ts`가 등록)가 메모리에서 지웁니다. 같은 작업이 날짜가 지난 주행 상태, 만료된 초대 코드, 하루가 지난 가족 만들기 기록, 30일 쓰지 않은 구성원, 24시간 쓰지 않은 '혼자뿐인 빈 가족'도 정리합니다. 작업은 주입 시계(`now`)로 스스로 판정해 5분마다 불려도 안전하고, 판정은 `createApp({ now })`와 같은 시계로 테스트합니다.
- **정책서 원문과 다른 점(완료 보관)**: 원문은 '완료되면 삭제'지만 **완료·거절된 요청도 그날(서울 날짜)이 끝날 때까지 둡니다**. 이유: 보낸 사람 폰은 앱이 앞에 있을 때만 폴링하므로 완료 즉시 지우면 '도착했어요'·'이번엔 어려워요'를 한 번도 못 볼 수 있습니다. 차가 받는 목록(`GET /requests?driver=`)에는 끝난 요청이 오지 않으므로 차에는 영향이 없습니다. (이전 안은 완료 1시간 보관이었으나 거절과 기준을 같게 했습니다.)
- 구성원이 나가는 모든 경로(나가기·30일 정리·밀려남)는 그 사람의 요청과 알림을 지우고, 그 차에 가족 자리가 안 남으면 '우리 차' 요청도 지웁니다.

## 기존 '일정을 가족에게 보내기'와의 관계

`POST /schedules/:id/family-request`와 픽스처 가족(`fixtures/family/members.json`, `GET /family/members`·`GET /family/requests`)은 폰 3단계 화면과 Maestro가 쓰고 있어 **그대로 동작합니다**(기본 자리·데모 경로, 응답 계약 `status: 'delivered'` 고정). 새 모델에서 이것은 **'약속 가기' 요청의 한 형태**(일정 하나를 가족에게 보내기)입니다: 새 모델의 약속 가기는 `POST /requests`의 `category: 'appointment'`이고 상태가 보냄 → 전달 → 수락(출발했어요) → 완료(도착했어요)로 움직입니다.

내부적으로 같은 저장소를 쓰지는 않았습니다(가능하면 쓰라는 요청을 의식한 판단): 옛 경로의 받는 사람은 실제 가족 구성원이 아니라 픽스처 가족이고, 응답이 `status: 'delivered'` 하나로 고정돼 있으며(받는 쪽이 없는 데모), `GET /schedules/places`의 일정별 `familyRequests`가 자리 데이터(`SeatData.family`)를 읽습니다. 합치면 폰 화면 계약이 바뀌므로, 폰 가족 탭(J10b)이 새 모델로 옮겨 가면 옛 경로를 `POST /requests`의 약속 가기로 대체하고 `SeatData.family`·픽스처 가족을 지웁니다. **J10b는 옛 경로를 대체하지 않고 그대로 두었습니다**(데모·기존 Maestro가 쓰므로): 가족 탭 맨 아래 '일정으로 보내기'가 `FamilySendScreen`(픽스처 가족, '전달됨')의 입구로 남아 있고, 새 가족의 '약속 가기'(요청 만들기)와 문구로 구분합니다. 옛 입구를 없애는 것은 데모·E2E를 새 모델로 옮긴 뒤의 일입니다. 새 모델의 받는 사람으로 픽스처 가족 id를 쓰면 400입니다.

## 폰 가족 탭(J10b)이 알아야 할 점(계약 쪽 정리)

- **구성원 비밀값을 저장하고 보내야 합니다.** `POST /family/invite`·`/join` 응답의 `memberToken`은 **그 응답에만** 있으므로 받자마자 `expo-secure-store`에 저장하고(저장 전에 앱이 죽으면 새로 참여해야 함), 이후 `/family/*`·`/requests` 호출마다 `X-Chagok-Member`로 보냅니다. 기기 id(`X-Chagok-Device`)는 가족 기능에 쓰지 않습니다.
- 차에 연결한 폰은 **연결 뒤 첫 가족 호출(또는 가족 만들기·참여)에 비밀값과 폰 토큰(`Authorization: Bearer`)을 함께** 보내야 자리가 구성원에게 묶입니다(묶여야 '차 연결됨'·'우리 차'·요청 전달이 됨). 이후에는 둘 다 늘 보내면 됩니다(다른 차로 다시 연결하면 새 폰 토큰과 비밀값을 같이 보내는 첫 호출에서 옮겨 감).
- 연결을 끊거나 차곡이 초기화돼 폰 토큰이 죽어도(401) 폰은 토큰만 버리고 **비밀값으로 계속 가족을 씁니다**. 401 `unknown-member`(나갔거나 30일 비활동·혼자뿐인 빈 가족 정리·가족 수 상한으로 밀려남)를 받으면 저장한 비밀값을 지우고 가족을 새로 만들거나 참여합니다. 앱을 지워 비밀값을 잃었으면 새로 참여해야 합니다(옛 구성원은 30일 뒤 정리).
- 흐름: `GET /family`(없으면 `family: null`, 식별이 없으면 401이라 비밀값이 없는 새 폰은 `POST /family/invite`·`/join`으로 시작) → 초대(`POST /family/invite`) 또는 참여(`POST /family/join`) → 요청 만들기(`POST /requests`, '우리 차'는 `cars`에서 `carRef`를 고름) → 상태(`GET /requests`, `sent[].status`·`drivingNow`·`etaStage`, 알림 `family-status`의 `requestId`).
- 폰이 계산해야 하는 문구: 상태 코드 × 카테고리(위 표). 보냄 문구는 `drivingNow`(약속·픽업만 참 가능), 픽업의 '곧 도착해요'는 `etaStage`. 요청 모양에 바뀐 시각은 없습니다.
- `received`에는 `drivingNow`·`etaStage`가 없습니다(내 도착 예정을 누구에게 보여 줄지는 `members[].shareWithThem`과 `PUT /family/share`).
- 약속·픽업의 시각이 이미 지났으면 400이라 폰이 미리 막거나 오류를 보여 줍니다. '우리 차' 요청은 그 차에 가족 자리가 사라지면 서버가 지우므로 보낸 요청이 목록에서 사라질 수 있습니다.

## 폰 가족 탭 화면과 저장 방식 (J10b)

코드는 `phone/src/features/family/`(가족 탭 `FamilyTabScreen`, 요청 만들기 `FamilyRequestScreen`)에 모여 있고 문구는 `phone/src/i18n/ko.ts`의 `family`·`familyRequest`·`familyTab`입니다. 테스트는 `phone/src/features/family/__tests__/`입니다.

### 구성원 비밀값과 헤더

| 파일 | 하는 일 |
| --- | --- |
| `memberSecret.ts` | 구성원 비밀값(`memberToken`)을 `expo-secure-store`(키 `chagok.familyMemberToken`)에 두는 `MemberSession`. 처음 읽을 때 한 번만 불러와 메모리에 두고(저장소가 막혀도 이번 실행 동안은 메모리 값), 서버 모양(32~128자 영문·숫자·`-`·`_`)이 아닌 값은 없는 것으로 봅니다. 값이 생기거나(쓰지 못했으면 `persisted: false`) 지워질 때(이유 `left` 내가 나감 / `gone` 서버가 모름) 구독자에게 알립니다. 저장소에 쓰지 못하면 화면이 '이 폰에 가족 정보를 저장하지 못했어요. 앱을 닫으면 가족에서 나온 것처럼 보일 수 있어요.' 한 줄로 안내합니다. **폰 토큰(`api/session.ts`)과 따로 둡니다: 차 연결을 끊어도 지우지 않습니다.** |
| `familyClient.ts` | `/family/*`·`/requests`를 부르는 Hono RPC 클라이언트(`hc<AppType>`). 요청마다 비밀값이 있으면 `X-Chagok-Member`, 폰 토큰이 있으면 `Authorization: Bearer`를 **함께** 보냅니다(연결 뒤 첫 가족 호출도 같음: 서버가 자리를 구성원에 묶음). 기기 id(`X-Chagok-Device`)는 보내지 않습니다. |
| `familyGroupApi.ts` | 호출 모음(`fetchFamily`·`invite`·`join`·`rename`·`leave`·`setShare`·`fetchRequests`·`createRequest`). 만들기·참여 응답의 `memberToken`을 **받자마자 저장한 뒤** 화면에 돌려주고, 나가기는 비밀값을 지웁니다. 저장한 비밀값도 폰 토큰도 없으면 서버에 묻지 않고 '가족 없음'입니다. 서버 거절은 `FamilyHttpError`(`status`·`reason`·`retryAfterSeconds`)로 던집니다. |

**401 처리는 이유로 가릅니다**(`familyClient.ts`): `reason: 'unknown-member'`(나갔거나 오래 쓰지 않아 정리됨, 서버를 다시 켬)면 저장한 비밀값만 지우고 응답을 그대로 돌려줍니다(화면은 '가족에서 나왔어요'). 그 밖의 401(폰 토큰이 죽음: 연결 끊김·초기화)은 폰 토큰만 버리고 같은 요청을 비밀값만으로 한 번 다시 보냅니다. 기존 `withSessionReset`을 그대로 쓰지 않은 이유는, 비밀값이 죽어 받은 401에도 멀쩡한 폰 토큰을 버리게 되기 때문입니다. 서버는 폰 토큰을 먼저 검사하므로 둘 다 죽었으면 다시 보낸 요청의 401(`unknown-member`)에서 비밀값도 지웁니다.

타입 한계: 서버 라우트 타입은 `POST /requests` 입력을 검증을 거친 모양(`{ fields, recipient, … }`)으로 추론하고, 응답의 카테고리별 항목(`item`·`place` …)도 `Omit` 때문에 타입에 담기지 않습니다. 그래서 본문은 `as never`로 보내고(`createRequest`) 응답은 `requestModel.ts`의 `normalizeRequest`가 모양을 직접 확인해 화면 모델(`SentRequest`·`ReceivedRequest`)로 바꿉니다(모르는 카테고리·상태나 모자란 항목은 버립니다).

가족이 나 혼자뿐이면 보낼 사람이 없으므로 초대 코드 구역이 맨 위에 오고, 가족이 모이면 요청 구역이 위로 올라옵니다. 저장(만들기·참여·초대 코드·이름·나가기·공유)은 **한 번에 하나**만 보내고(`useFamilyGroup`), 저장이 시작되면 진행 중인 조회를 취소하며, 화면이 사라져도 보낸 저장은 취소하지 않습니다(만들기·참여 응답에만 있는 비밀값을 놓치지 않으려고).

**만들기·참여·새 초대 코드는 10초 시간 제한으로 요청을 끊지 않습니다.** 끊으면(fetch abort) 서버는 가족·구성원을 이미 만들었는데 응답에만 있는 `memberToken`을 폰이 놓치고, 다시 누르면 가족이 또 생기거나 '엄마 2' 같은 고아 구성원이 생기기 때문입니다. 10초가 지나면 화면은 '서버 응답을 확인하는 중이에요. 끝날 때까지 같은 버튼을 다시 누르지 않아도 돼요.'(`slow`)로 바꾸고 계속 기다리며, 그동안 가족 구역의 모든 저장 버튼은 막혀 있습니다. 늦게 온 응답도 비밀값을 저장하고(화면이 사라졌어도 `familyGroupApi`가 응답을 받자마자 저장) 화면에 반영합니다. 응답이 90초(`PATIENT_ACTION_MS`)까지 없을 때만 포기하고 '이미 처리됐을 수 있으니 가족 탭을 다시 열어 확인'하라고 안내합니다(이때만 비밀값을 놓칠 수 있고, 만들다 만 혼자뿐인 빈 가족은 서버가 24시간 뒤 정리합니다). 이름 바꾸기·나가기·공유는 그대로 10초 제한입니다. 조회는 새 조회가 시작되면 이전 조회를 취소하고 응답을 반영하기 전에 그 요청의 controller가 아직 현재 것인지 확인합니다. 오류 문구는 서버 `reason`으로 가릅니다(`invalid`·`already-in-family`·`family-full`·`locked`(남은 초 표시)·`rate-limited`·`too-many-families` 등).

### 요청 만들기(정책 10.10 '카테고리 → 받는 사람 → 장소·시간 → 한 줄 메모')

- 카테고리 4종: 채비(물건, 가져갈 때/가져올 때), 들르기(장소, 살 것·찾을 것, 기한 오늘 중 또는 몇 시까지), 약속 가기(시각, 장소, 함께 가는 사람), 데려다주기·픽업(누구를, 어디서, 어디로, 몇 시). 카테고리를 고르면 받는 사람·내용·메모·[보내기]가 나옵니다.
- 받는 사람: 가족 한 사람(차 연결 여부 표시) 또는 '우리 차'(`GET /family`의 `cars`, **차가 없으면 선택지에 안 보이고** 이유를 안내, 차가 둘이면 '우리 차 1·2').
- 장소 칸: 글자를 적거나 [장소 찾기]로 기존 장소 검색 화면(`PlaceSearchScreen`, `pickerKey` 모드)을 엽니다. 고르면 **글자(장소 이름) + 좌표**가 함께 들어가고(서버에 저장하지 않음), 검색어를 넣으면 '‘…’ 그대로 쓰기'로 좌표 없이 글자만 보낼 수 있으며(검색을 못 쓸 때도), 칸의 글자를 직접 고치면 좌표를 버립니다. 고른 장소는 `features/places/placePicker.ts`(키별 한 곳 구독)로 돌려받습니다.
- 날짜는 오늘·내일(서울)만, 시각은 숫자 키패드(`1830` 또는 `18:30`)로 받아 `HH:MM`으로 맞추고 `+09:00` ISO로 보냅니다. 약속·픽업의 시각, 들르기 '몇 시까지'(오늘의 이미 지난 시각)가 지금보다 앞서면 폰이 먼저 막습니다(서버는 10분 여유). **지난 시각 오류를 서버 문장으로 가르지 않습니다**: 폰 검증이 먼저 걸러 서버 `bad-request`는 모두 '입력한 내용을 다시 확인해 주세요'입니다.
- **자정 경계**: 폼을 연 때의 서울 날짜를 기준으로 '오늘·내일'을 고정하고, 보낼 때 서울 날짜가 바뀌었으면 보내지 않고 '날짜가 바뀌었어요. 오늘·내일을 다시 확인한 뒤 보내 주세요.'로 다시 확인하게 합니다(다시 누르면 새 기준 날짜로 보냄).
- 고른 장소 이름이 서버 길이 제한(100자)을 넘으면 폰이 100자로 잘라 넣습니다(좌표는 그대로).
- 메모는 한 줄(줄바꿈은 공백)로 100자까지, 30자를 넘으면 '차는 메모가 있어요라고만 말해요' 안내(막지는 않음).
- 서버 오류: 400 `bad-request`, `self`, `unknown-car`·`unknown-recipient`(받는 사람을 비우고 가족을 다시 읽음), 409 `not-in-family`, 429 `too-many-requests`. 네트워크·시간 초과·5xx는 서버가 받았는지 알 수 없어, **폰이 보낸 목록을 다시 읽어** 방금 보낸 것과 같은 요청(카테고리·받는 사람·핵심 항목·메모가 같고 보내기 시작한 때(시계 어긋남 2분 여유) 이후에 만들어진 것, `matchesSent`)이 있으면 이미 보내진 것으로 보고 그 요청으로 이동하고, 없다고 확인됐을 때만 '목록을 확인했는데 이 요청은 없어요. 다시 보내 주세요'로 다시 보내기를 허용합니다. 목록도 읽지 못하면 '이미 보내졌을 수 있으니 가족 탭의 보낸 요청을 확인'하라고만 안내합니다. 확인하는 동안에는 보내기를 다시 누를 수 없습니다. **서버의 중복 방지 키(idempotency key)는 후속 과제입니다**(폰 쪽 확인은 서버가 아직 처리 중인 요청을 놓칠 수 있는 작은 틈이 있음).
- 보내면 가족 탭으로 돌아가 그 요청을 맨 위에 표시합니다(`router.navigate({ pathname: '/family', params: { request: id } })`).

### 상태 문구(`requestModel.ts`의 `senderStatusLabel`)

정책 10.10 표와 위 '상태 전이 표'를 그대로 옮긴 표이고 테스트(`requestModel.test.ts`)가 카테고리 × 상태 × `drivingNow` × `reachable` × `etaStage`를 모두 고정합니다.

| 카테고리 | 보냄 | 전달 | 수락 | 완료 |
| --- | --- | --- | --- | --- |
| 채비 | 차에 타면 전해요 | 전달했어요 | (없음) | 챙기라고 전했어요 |
| 들르기 | 〃 | 전달했어요 | 수락했어요 | 들렀어요 |
| 약속 가기 | 〃 | 전달했어요 | 출발했어요 | 도착했어요 |
| 데려다주기·픽업 | 〃 | 전달했어요 | 수락했어요 | 도착했어요 |

- 거절(들르기·약속·픽업)은 '이번엔 어려워요'.
- 보냄: `drivingNow`가 참이면 '운전 중이라 다음 정차 때 전해요'(받는 사람이 도착 예정 공유를 켠 약속·픽업만 서버가 참을 줌), 그렇지 않고 받는 사람 폰이 어느 차에도 연결되지 않았으면(`reachable` 거짓) '폰 앱에서만 볼 수 있어요', 그 밖에는 '차에 타면 전해요'.
- `etaStage: 'soon'`은 전달·수락 상태의 약속·픽업에서 '곧 도착해요'로 바꿉니다. 문구에 '5분 뒤' 같은 시간을 넣지 않습니다: 서버는 도착 5분 전 신호를 받은 사실(`etaStage`)만 주고 시각은 주지 않아, 시간이 지나도 화면 글자가 그대로이기 때문입니다. (서버 알림 문구 `phrases.ts`의 약속 '5분 뒤 도착해요'는 알림이 오는 순간의 글이라 그대로 두었고, 알림함에 남은 알림과 상태 화면 문구가 다를 수 있습니다. 서버 문구를 맞추는 것은 후속 과제입니다.)
- 받는 사람 폰의 문구(정책서에 표가 없어 가안): 보냄 '차에 타면 전해 드려요'(내 폰이 차에 연결되지 않았으면 '차에 연결하면 전해 드려요'), 전달 '차에서 전했어요', 수락 '수락했어요', 거절 '거절했어요', 완료 '끝났어요'.

### 새로 고침

`useFamilyRequests`: 화면이 포커스를 얻을 때 읽고, 가족 탭이 열린 채 `request` 파라미터만 바뀌어도(알림 누름·오늘 탭 누름) 바로 다시 읽습니다. 새로 읽은 목록에도 그 요청이 없으면 '요청을 찾을 수 없어요. 이미 지워졌거나 날짜가 지났을 수 있어요.' 한 줄을 보입니다(읽기 전의 옛 목록으로 잘못 알리지 않도록 파라미터가 바뀐 때의 읽은 횟수(`reads`)보다 더 읽은 뒤에만 판단). 또한 포커스가 있고 앱이 앞에 있는 동안 **45초**(`REQUESTS_POLL_MS`, 알림 폴링 60초와 박자가 겹치지 않게)마다 다시 읽습니다. 앱이 뒤로 가면 멈추고 앞으로 오면 바로 읽고 이어 갑니다. 한 번에 하나만 돌고(새 조회가 이전 조회를 취소, 늦은 응답은 버림) 이미 목록이 있으면 주기 조회가 실패해도 화면을 오류로 바꾸지 않습니다. 가족 탭과 오늘 탭이 같은 훅을 씁니다. **가족이 없으면 요청을 묻지 않습니다**: `familyGroupApi`가 `GET /family`·만들기·참여·나가기로 '가족에 속하는지'를 기억하고(모르면 먼저 `GET /family`로 확인: 폰 바꾸기 뒤 새 폰은 비밀값 없이 폰 토큰만으로 같은 구성원일 수 있어서), 속하지 않으면 `GET /requests`를 생략하고 `family: false`를 돌려주며 훅은 그때 주기 조회를 멈춥니다(포커스·앞으로 올 때·직접 읽기는 그대로 읽음). 저장한 비밀값도 폰 토큰도 없으면 서버에 아무것도 묻지 않습니다.

### 오늘 탭의 받은 가족 요청, 알림 누름

- 오늘 탭 `family-inbox` 구역(`ReceivedRequestsSection`): 받은 요청을 최대 3개(진행 중인 것 먼저, 나머지는 'N개 더 보기' → 가족 탭) 보이고, 누르면 가족 탭에서 그 요청을 엽니다. **받는 사람 폰에는 알림을 보내지 않으므로 화면 표시가 전부**입니다(정책 10.6). 가족이 없으면 서버에 묻지 않고 빈 상태입니다. 구역 순서는 정책 10.7대로 오늘 일정 → 받은 가족 요청 → 장소 빈 일정(배너·다른 날 빈 일정)입니다.
- **가족에서 나가면(구성원 비밀값이 지워지면: 나가기·서버가 모르는 구성원) 폰 알림함의 `family-status` 알림을 모두 지웁니다**(`familyInboxCleanup.ts`): 그 알림이 가리키던 요청은 서버에서 이미 지워졌고, 폰 알림함에 7일 남으면 가족이 아닌 사람의 요청 상태가 홈에 계속 보입니다. 이미 시스템 알림 창에 떠 있는 알림은 지울 수 없습니다.
- **알림함에는 도착 예정 시각(`etaAt`)을 두지 않습니다**(`notifications/inbox.ts`의 `dropEta`): 폰은 `etaAt`을 쓰지 않고(제목·본문과 `requestId`만 씀), 정책 11장은 가족에게 보인 도착 예정 시각을 저장하지 않는다고 하므로 담을 때와 저장소에서 불러올 때 버립니다(서버 알림함은 도착 예정 알림을 최대 1시간만 둠). 옛 버전이 저장한 값도 다음에 불러올 때 지워 저장소에 다시 씁니다.
- 알림 누름: `registerTapHandler('family-status', …)`(`familyTaps.ts`, 루트 레이아웃이 불러와 등록)가 `data.requestId`로 가족 탭의 그 요청을 엽니다(요청 id가 없으면 가족 탭만). 도착 예정 알림(5분 전·도착)도 같은 `family-status`라 같은 화면으로 갑니다.

### 폰 E2E

`e2e/maestro/phone/family.yaml`(`E2E_FLOWS=family pnpm e2e:phone`, 다른 flow와 섞어 돌리지 않음): 가족 만들기 → 초대 코드 표시 → 서버에 두 번째 구성원(엄마) 참여(`family-join.js`) → 도착 예정 공유 켜기(서버 확인) → 들르기 요청(장소 검색) → '폰 앱에서만 볼 수 있어요' → 엄마 폰을 차에 연결(`family-connect.js`) → '차에 타면 전해요' → 차가 전달·수락·완료로 바꿀 때마다(`family-status.js`) 문구 갱신 → 우리 차로 채비 → 엄마가 보낸 약속(`family-send.js`)을 오늘 탭 '받은 가족 요청'에서 열기 → 가족에서 나가기(서버 확인 `family-assert.js`). 가족 API는 구성원 비밀값으로 식별하므로 기기 id 없이(`EXPO_PUBLIC_DEVICE_ID=none`) 돕니다.

### 이 묶음이 서버 계약에서 아쉬웠던 점

- `POST /requests`가 멱등이 아니라(요청 id를 클라이언트가 정할 수 없음) 응답을 놓친 재시도가 중복 요청을 만들 수 있습니다. 폰은 실패 뒤 보낸 목록을 읽어 같은 요청이 있는지 확인해 막지만, 서버가 아직 처리 중인 요청은 놓칠 수 있습니다. **서버 idempotency key(요청 id를 클라이언트가 정하거나 `Idempotency-Key` 헤더)는 후속 과제**입니다.
- 서버 알림 문구(`phrases.ts` `soonBody`)의 약속 '5분 뒤 도착해요'와 폰 상태 문구 '곧 도착해요'가 다릅니다(위 상태 문구 절).
- 폰 바꾸기(replace) 뒤에도 **옛 폰의 구성원 비밀값은 서버가 취소하지 못합니다**: 새 폰은 폰 토큰만으로 같은 구성원이 되지만, 옛 폰의 secure-store에는 비밀값이 남아 옛 폰이 계속 같은 구성원으로 가족 API를 쓸 수 있습니다(비밀값 교체·폐기 API가 없음). 한계로 둡니다.
- 받는 사람 모양(`received`)에는 `drivingNow`·`etaStage`가 없고 바뀐 시각도 없어, 받는 사람 폰의 상태 문구는 코드만으로 만든 가안입니다.
- `GET /family`에 초대 코드가 `ABCD-EFGH`(하이픈 포함)로 오지만 `POST /family/join`은 대소문자·하이픈을 무시하므로 폰은 입력을 그대로 보냅니다.
- 서버 응답 타입이 카테고리별 항목을 담지 못하고(`Omit`된 합집합) `POST /requests` 입력 타입이 검증 뒤 모양으로 추론되어 폰이 형변환·직접 검증을 합니다(서버 라우트 타입 정리 필요).
- 알림 누름으로 가족 탭에 갈 때 그 요청이 이미 지워졌으면(날짜 지남·상대가 나감) 목록에 없어 '선택한 요청' 표시가 나타나지 않고 가족 탭만 열립니다.

## 차(C) 쪽 묶음이 알아야 할 점

- 모든 호출은 **차 토큰 + `driver=<자리 id>`**입니다(`driver` 없으면 400, 옛 차 앱 호환 없음, 빈 값·그 차의 자리가 아니면 403). 같은 사람이 탄다고 판단한 자리로 부릅니다. 차의 호출은 그 자리의 구성원이 가족 API를 쓴 것으로 세어 30일 비활동 정리에서 제외합니다.
- 탑승·정차 때 `GET /requests?driver=<자리>&date=<오늘>`로 받습니다(그 자리 몫과 '우리 차' 몫이 함께 옴, `via`로 구분). 끝난 요청은 오지 않습니다. '우리 차' 몫은 그 차에 그 가족의 자리가 남아 있을 때만 옵니다(차곡을 초기화하거나 가족 폰이 모두 끊기면 사라짐).
- 말한 뒤 `PATCH`로 `delivered`, 수락하면 `accepted`, 거절하면 `declined`, 도착·하차 체크에서 말하면 `completed`. 같은 상태 재시도는 안전합니다. 무응답은 상태를 바꾸지 않습니다(다음 정차 때 한 번 더 묻는 것은 차의 몫).
- 주행 시작·멈춤마다 `POST /drive-state`. 약속·픽업은 도착 5분 전에 `POST /requests/:id/eta`(`soon`, 도착 예정 시각을 `etaAt`으로), 도착 시 `arrived`(그 뒤 `completed`). 공유 여부는 서버가 판단하므로 차는 늘 보내면 됩니다.
- 늦을 때 연락의 기본 상대는 요청을 보낸 가족입니다. 요청의 `from`(구성원 id·이름)을 쓰고, 연락 요청(`POST /notify/late`)은 다른 묶음입니다.

## 가안·한계

- 가안(정책서 13장·12장 미결): 초대 코드 24시간, 한 가족 6명, 요청 날짜 오늘·내일, 지난 시각 여유 10분, 구성원 비활동 30일, 혼자뿐인 빈 가족 24시간, 주소별 가족 만들기 10분 10개·하루 20개, 진행 중 요청 한도(사람 30·가족 100), 가족 300개, 도착 예정 알림 보관 1시간, 알림 문구. 모두 `family/limits.ts`·`family/phrases.ts` 한 곳입니다.
- 정책서 12장 '들르기 묶는 거리 3km'와 '픽업 곧 도착 알림 5분 전'은 차가 판단하는 값이라 서버에는 상수가 없습니다(차가 5분 전에 `eta`를 부름).
- 저장은 메모리뿐입니다(서버를 다시 켜면 가족·요청·공유·주행 상태가 사라지고, 폰은 `family: null`을 받아 다시 묶어야 함). 영속화할 때는 알림 중복 억제 키(`notifier`)도 같이 영속화해야 합니다(`docs/notifications.md`).
- 보낸 사람이 요청을 취소하는 API는 없습니다(정책서 API 표에 없음). 폰에도 취소 버튼이 없습니다.
- 구성원을 다른 구성원이 내보내는 API는 없습니다(나가기만).
- 초대 코드는 인원이 찰 때까지 만료 전에 여럿이 쓸 수 있습니다(위 초대 코드 항목). 요청 주소가 프록시 뒤에서 하나로 보이면 시도 제한·가족 생성 제한이 모든 사용자에게 걸리므로 배포 때 `clientAddress`를 바꿔야 합니다.
- 서버를 `HOST=0.0.0.0`으로 열면 구성원 비밀값(256비트 난수)과 폰 토큰이 평문 HTTP로 오가므로 HTTPS가 필요합니다. 식별 없이 가족을 만들 수 있어(남용은 주소별 상한과 정리로 제한) 가족 수 상한이 찬 서버에서는 혼자뿐인 빈 가족(설정 중인 사람 포함)이 밀려날 수 있고, 그때는 401 `unknown-member`로 폰이 알게 됩니다.
- 구성원 비밀값은 서버 메모리에 그대로 둡니다(토큰 해시 저장은 DB로 영속화할 때). 서버를 다시 켜면 모든 가족·비밀값이 사라지고 폰은 401로 알아 새로 참여합니다.
- 구성원 비밀값과 폰 토큰은 둘 다 가진 쪽만 자리를 묶을 수 있지만, 폰 바꾸기(자리 이어받기)를 한 새 폰은 그 자리의 구성원이 됩니다(차 화면의 새 코드를 가진 사람 = 그 자리의 주인이라는 연결 모델과 같음).
