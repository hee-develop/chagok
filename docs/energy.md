# 에너지 후보 서버 (`POST /energy/options`)

정책서 9장 '에너지 체크'의 서버 쪽입니다. 차가 "필요 거리가 주행 가능 거리의 90%를 넘는다"고 판단한 뒤 부르면, 서버가 **충전소·주유소 후보**를 정렬해 돌려줍니다. 필요 거리·90% 판단·연료 종류 읽기는 차의 몫이라 서버는 하지 않습니다.
외부 API(환경부·오피넷)는 서버만 부릅니다. 키는 서버에만 두고 로그·응답에 남기지 않습니다.

## 요청

```json
{
  "fuel": "ev",
  "origin": { "lat": 35.1595, "lng": 126.8526 },
  "destination": { "lat": 35.1681, "lng": 126.8888 },
  "stayMinutes": 180,
  "at": "2026-11-06T12:00:00+09:00"
}
```

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `fuel` | 예 | `ev` · `gasoline` · `diesel` · `hybrid`. 하이브리드는 휘발유 가격으로 봅니다 |
| `origin` | 예 | 현재 위치(경로 출발점). 위도 -90~90, 경도 -180~180 |
| `destination` | 예 | 대상 일정 장소(경로 도착점). 같은 범위 |
| `stayMinutes` | 아니오 | 대상 일정이 머무는 시간(분). 0~10080. 없으면 '오래 머무는 일정'이 아닌 것으로 봅니다 |
| `at` | 아니오 | 제안 시점(오프셋 있는 ISO8601). 식사 시간대 판단에만 쓰고, 없으면 서버 시계입니다 |

모르는 필드는 무시합니다. 잘못된 값(없거나 형식·범위가 틀린 값, JSON이 아님)은 400 `{ "error": "..." }`, 본문이 64KB를 넘으면 413, **같은 요청 주소에서 분당 20회를 넘으면 429**(`Retry-After` 초, 잘못된 요청도 횟수에 셉니다)입니다. 차 한 대의 정상 사용(제안 직전 한 번, 거절하면 한두 번 더)은 분당 한 자릿수라 막히지 않는 값입니다(가안, `constants.ts`). 요청 주소는 연결의 원격 주소이고 `X-Forwarded-For` 같은 헤더는 믿지 않으므로, 프록시 뒤에서는 프록시 주소 하나로 셉니다.

## 응답 (200)

```json
{
  "fuel": "ev",
  "source": "fixture",
  "stage": "destination",
  "mealBundle": false,
  "partial": false,
  "stale": false,
  "asOf": null,
  "candidates": [
    {
      "id": "EX-GJ-001",
      "kind": "slow_charger",
      "name": "예시 챔필 주차장 충전소",
      "address": "가상시 가상구 예시로 12",
      "lat": 35.1692, "lng": 126.887,
      "detourMeters": 204,
      "routeProgress": null,
      "charger": { "stationName": "예시 챔필 주차장 충전소", "status": "available", "availableCount": 2, "totalCount": 3, "powerKw": 7, "parkingFree": true },
      "price": null,
      "brand": null,
      "hasFood": null
    }
  ]
}
```

- `source`: `fixture`(목) · `live`(실제 API) · `unavailable`(외부 조회 실패·제한 시간 초과). **`unavailable`이면 `candidates`가 비어 있고, 후보가 없어서 빈 것이 아닙니다.** 차는 이때 에너지 제안을 건너뛰거나 나중에 다시 묻습니다. 실패해도 HTTP 상태는 200이고 서버는 계속 돕니다.
- `stage`: `destination`(목적지 근처 완속) · `route`(경로상 휴게소 급속 또는 주유소) · `none`(후보 없음 또는 조회 실패).
- `mealBundle`: 식사 시간대이고 **맨 앞 후보(`candidates[0]`)가 식사할 수 있는 휴게소일 때만** true(전기차 `route` 단계). 차가 '휴게소 식사 + 급속 충전'을 한 제안으로 묶을지 판단하는 재료이고, 묶는 후보는 항상 `candidates[0]`입니다(맨 앞이 식사 불가인데 뒤에 식사 가능 후보가 있다고 true가 되지 않습니다). 후보마다 `hasFood`도 있습니다.
- `partial`: true면 **일부 지점·휴게소 조회, 또는 경계 근처 이웃 시도 받기만 실패**해 받은 결과로 답한 것입니다. 후보가 더 있을 수 있고, 후보가 비어 있어도(`stage: "none"`) 없다고 단정할 수 없습니다. 차는 받은 후보로 제안하되 "다른 곳은 찾지 못했어요."처럼 끝을 단정하지 않는 편이 안전합니다. **전부 실패하면 `partial`이 아니라 `source: "unavailable"`**입니다.
- `stale`·`asOf`: **충전기 상태를 새로 받지 못해 5분보다 낡은 데이터(최대 30분)로 답했을 때** `stale: true`이고 `asOf`가 그 데이터를 받은 시각(ISO8601, UTC, 쓴 데이터 가운데 가장 낡은 것)입니다. "빈 충전기 2대"가 그만큼 낡았을 수 있다는 뜻이라, 차는 말로 단정하지 말고("빈 곳이 있을 수 있어요") 카드에 확인 문구를 두는 편이 안전합니다. 새로 받은 데이터·목·주유소 응답은 `stale: false`, `asOf: null`입니다. 30분이 넘은 데이터는 버리므로 그 이상 낡은 값은 나오지 않습니다(그때는 `unavailable`).
- `candidates`: 정렬된 후보, 최대 5개. 차의 '다른 데·다른 휴게소'는 다음 후보를 쓰면 됩니다(정책서 7장 '대안': 다음 후보 하나만 보이고 없으면 "다른 곳은 찾지 못했어요."). 5개를 다 쓰면 다시 부르지 말고 그 문구로 마무리하세요.
- 후보 필드
  - `kind`: `slow_charger` · `fast_charger` · `gas_station`
  - `name`: 충전은 목적지 충전소 이름 또는 **휴게소 이름**, 주유소는 주유소 이름. 말할 때 쓸 이름입니다
  - `lat`·`lng`: 길안내(`addWaypoint`)에 넣을 좌표. 휴게소 후보는 휴게소 좌표입니다
  - `detourMeters`: `destination` 단계는 목적지에서의 거리, `route` 단계는 출발→목적지 선분에서 벗어난 거리(직선 근사)
  - `routeProgress`: 선분 위 위치(0=출발, 1=도착). `destination` 단계는 null
  - `charger`(충전 후보만): `status` `available`(빈 충전기 있음)·`busy`(전부 충전 중)·`unknown`, `availableCount`/`totalCount`(같은 속도 충전기), `powerKw`(모르면 null), `parkingFree`(모르면 null)
  - `price`(주유소만): `{ fuel: "gasoline"|"diesel", won }` 원/L, `brand`(오피넷 브랜드 코드, 없으면 null)
  - `address`: 충전소 주소(주유소는 null — 오피넷 반경 조회 응답에 주소가 없습니다)

## 규칙

### 전기차 (`fuel: "ev"`)

1. `stayMinutes >= 120`이면 목적지 **500m 안**의 **빈(available) 완속 충전기**가 있는 충전소를 목적지에 가까운 순으로 줍니다(`stage: "destination"`). 전부 사용 중·점검인 충전소는 뺍니다.
2. 1이 해당하지 않거나 후보가 없으면 **경로상 휴게소의 급속 충전소**를 줍니다(`stage: "route"`). 휴게소는 `fixtures/energy/rest-stops.json`에서 출발→목적지 선분 3km 안인 것만 고르고, 휴게소 300m 안의 급속 충전기가 있는 곳만 후보가 됩니다. 급속 충전기가 전부 운영중지·점검인 휴게소는 뺍니다.
3. 정렬: **식사 시간대면 '빈 급속 충전기 + 식사 가능' 휴게소를 맨 앞으로** → 충전 상태(빈 곳 → 모두 충전 중 → 알 수 없음) → 식사 시간대면 식사 가능한 휴게소 먼저 → 경로에서 벗어난 거리 → 경로 위치. `mealBundle`은 이렇게 정렬하고 5개로 자른 뒤의 `candidates[0]`이 식사 가능일 때만 true입니다(식사 가능 후보가 전부 충전 중이고 식사 없는 빈 곳이 맨 앞이면 false).
4. 식사 시간대(서울): 07:00~09:00, 11:00~14:00, 17:00~20:00 (끝 시각은 포함하지 않음, 가안).
5. **한계: 시내 단거리 전기차는 경로상 휴게소가 없어 `stage: "none"`이 됩니다.** 정책서대로 경로상 후보는 휴게소(급속 충전)만 봅니다. 도시 안 이동에서 `stayMinutes`가 2시간 미만이거나 목적지 500m 안에 빈 완속이 없으면 후보가 나오지 않습니다(목적지·경로 주변의 일반 급속 충전소는 보지 않습니다).

### 휘발유·경유·하이브리드

경로에서 **3km 이내**(선분 수직 거리) 주유소를 **가격 오름차순**(같으면 경로에 가까운 순)으로 줍니다. 맨 앞이 '가장 싼 곳'입니다.
경로를 따라 찾기 위해 선분 위 7km 간격 지점마다 반경 5km로 조회하고(오피넷 반경 상한 5km, 간격은 조회 중심을 0.005도 격자로 맞추는 이동분까지 감안한 값), **출발점에서 100km까지만** 훑습니다(검색 원 16개 이하, 같은 격자·연료는 5분 캐시라 실제 외부 호출은 그보다 적을 수 있음). 100km 밖 주유소는 후보가 아닙니다.

### '경로 3km 우회' 근사 (가안)

경로 모양을 모르므로 **출발→목적지 직선 선분까지의 수직 거리**로 근사합니다(끝은 끝점까지의 거리). 실제 도로 경로, 그리고 되돌아 나오는 실제 우회 거리(대략 2배)와 다릅니다. 선분 중간 위도 기준 평면 근사라 약 300km(광주→서울)에서 끝점 쪽 거리 오차가 약 1.5%까지 납니다(3km 경계가 수십 m 움직이는 정도).

## 어댑터와 환경 변수

`server/src/energy/`: 포트 `ChargerSource`·`FuelStationSource`·`RestStopSource`(`types.ts`), 픽스처 구현(`fixtureSources.ts`), 픽스처 파일 읽기(`fixtureFiles.ts`), 실제 구현(`evCharger.ts`·`opinet.ts`), 환경 변수로 고르는 `sources.ts`. 포트는 실패하면 던지고, 서비스(`options.ts`)가 잡아 `source: "unavailable"` + 빈 후보로 바꿉니다. 충전소 포트는 결과 말고 품질 정보(이웃 시도 실패, 낡은 캐시)를 `NearInfo`로 돌려주고, 서비스가 그것을 `partial`·`stale`·`asOf`로 모읍니다.

**`createApp`의 `energy` 옵션은 선택이고 기본값은 파일을 읽지 않는 빈 소스**입니다(`source: "fixture"`, 후보 없음). `fs`로 `fixtures/energy/`를 읽는 코드(`fixtureFiles.ts`)는 `app.ts`가 가져오는 모듈 밖에 있고, 서버 시작 코드(`index.ts` → `sources.ts`)와 테스트 도우미가 픽스처 목을 넘깁니다. 폰 앱이 `AppType`을 가져오며 서버의 `app.ts`와 그 import 그래프를 함께 타입체크하는데, 폰의 tsconfig는 `types: ["jest"]`만 싣습니다. 그 그래프에 `node:fs`·`process` 같은 node 전용 코드가 있으면 `/// <reference types="node" />`로 node 타입을 억지로 싣게 되고 폰 타입체크 프로그램에 `@types/node` 파일 83개가 들어옵니다(`pnpm --filter @chagok/phone exec tsc --noEmit --listFilesOnly | grep -c "@types/node"`로 확인, 기준선과 지금 모두 0). 다른 브랜치가 `createApp`을 `energy` 없이 불러도 깨지지 않습니다.

| 환경 변수 | 없을 때 | 있을 때 |
| --- | --- | --- |
| `EV_CHARGER_KEY` | `fixtures/energy/chargers.json` 목 | 환경부 전기차 충전소 API 호출 |
| `OPINET_KEY` | `fixtures/energy/fuel-stations.json` 목 | 오피넷 반경 내 주유소 API 호출 |

휴게소 목록은 항상 `fixtures/energy/rest-stops.json` 목입니다. 목 데이터는 전부 가상이고(이름 앞에 '예시', 주소는 실제 도로명·번지와 겹치지 않는 가상 값), 광주 시연 경로(육전집 → 챔피언스필드 / 광주 → 서울) 주변입니다.

- 외부 호출 제한 시간: 호출 하나 8초(오피넷), 환경부는 응답을 8초까지 기다림, 요청 전체 12초. 넘으면 `unavailable`. 요청 전체 제한 시간이 지나면 포트에 준 `AbortSignal`을 중단해, 나가던 오피넷 호출은 끊고 아직 나가지 않은 호출(대기열·남은 지점·휴게소 조회)은 나가지 않습니다.
- 키는 로그·응답·오류 메시지에 넣지 않습니다(오류 메시지는 고정 문구, 기록은 `[energy] 외부 조회 실패: <고정 문구>` 한 줄).
- 일부 조회만 실패하면 받은 결과로 답하고 `partial: true`, 전부 실패하면 `unavailable`입니다(목적지 완속 조회만 실패해도 경로상 휴게소 조회가 되면 그것으로 답합니다).

### 오피넷 호출 증폭 방지

- 조회 중심을 0.005도 격자(약 0.5km)로 맞춘 (좌표, 반경, 연료) 키로 **5분** 캐시합니다(최대 500항목, 가장 오래 안 쓴 것부터 버림, 만료 항목은 접근할 때 정리). 실패한 호출은 캐시하지 않습니다.
- 같은 키의 동시 호출은 하나로 합칩니다(기다리는 요청이 모두 떠나면 호출도 멈춤).
- 서버 전체에서 동시에 나가는 오피넷 호출은 4개까지, 그 위로 32개까지만 기다리고 넘으면 바로 실패(`unavailable`)합니다. 응답은 2MB까지만 읽습니다.
- 남한 영토 밖 좌표(북한·일본·중국 등)는 외부 호출 없이 빈 목록입니다. 경계는 `geo.ts`의 근사 다각형(본토)과 섬 상자(백령·연평·울릉·독도)이고, 휴전선은 몇 km 안의 근사라 선 바로 북쪽 몇 km는 안으로 들어올 수 있습니다(호출이 한 번 더 나갈 뿐입니다). 이어도·가거초 같은 해상 구조물은 뺐습니다.

### 환경부 호출 증폭·메모리 방지

- 시도 단위 데이터는 5분 캐시. 같은 시도의 동시 받기는 하나로 합치고, **서버 전체 동시 받기는 3개 시도, 응답 원문을 동시에 들고 있는 쪽은 2개**까지입니다(넘는 새 시도 받기는 시작하지 않고 실패, 쪽은 차례를 기다림). 받기는 호출자 한 명의 취소에 묶지 않고(묶으면 큰 시도는 영영 캐시가 안 채워집니다) 시도당 120초 제한 시간만 둡니다. 호출자는 8초까지만 기다립니다.
- **쪽은 받는 즉시 읽고 원문을 버립니다.** 한 쪽(9999건)은 약 9~11MB 응답이 글자 수 약 8백만 자(한글이 섞여 메모리에서는 약 16MB), 디코딩 중에는 바이트(`Uint8Array`)와 글자가 겹쳐 쪽 하나에 약 25~33MB가 필요합니다. 예전에는 시도마다 쪽 2개, 광주·전남은 코드 3개 x 2쪽, 시도 둘이면 그 두 배가 동시에 떠 있었습니다. 지금은 서버 전체에서 2쪽입니다. 같은 충전기가 여러 코드·쪽에서 오면 쪽이 오는 대로 한 번만 두므로, 옛 코드가 새 코드와 같은 데이터를 줘도 두 벌을 들고 있지 않습니다.
- **캐시에는 응답 원문을 붙잡지 않는 값만 둡니다.** V8은 13자 이상 문자열의 `slice`를 원문을 가리키는 '슬라이스'로 만들어, 충전소 이름 하나가 그 쪽 원문 전체(수 MB)를 살려 둡니다(`--allow-natives-syntax`의 `%DebugPrint`로 `SLICED_TWO_BYTE_STRING_TYPE` 확인). 그래서 쓰는 요소 14개만 읽고(`xmlRecords`의 `fields`), 숫자는 숫자로 바꾸고, 글자는 새 문자열로 복사하며(`strings.ts`의 `detach`: JSON 왕복), 같은 충전소의 충전기가 공유하는 충전소 ID·이름·주소·운영기관은 시도를 받는 동안만 쓰는 표로 한 번만 둡니다. 오피넷 주유소(5분 캐시, 최대 500항목)도 같은 방식으로 복사합니다.
- 실측(공식 예시 모양의 큰 쪽 15개 = 충전기 149,985대를 가짜 fetch로 받아 `--expose-gc`로 잼. 같은 프로세스에서 수정 전 커밋과 비교):

  | | 수정 전 | 수정 후 |
  | --- | --- | --- |
  | 캐시에 남는 힙(충전기 15만 대, 쪽 15개) | 298MB(충전기당 약 2.0KB) | 51MB(약 340바이트) |
  | 충전기 30만 대를 파서로 읽어 들고 있을 때 힙(`mem.mts`) | 419MB(RSS +613MB) | 96MB(RSS +166MB) |
  | 광주·전남(코드 3개 x 15쪽 = 45쪽)을 받는 동안 필요한 힙 상한(`--max-old-space-size`로 찾은 통과·실패 경계, 가짜 응답 생성 비용 포함) | 700MB 실패, 1000MB 통과 | 200MB 실패, 250MB 통과 |

  충전기 한 대는 객체 약 153바이트(위경도 숫자 상자 포함)에 글자를 더해 약 270~340바이트입니다. 서버를 띄우는 환경(메모리 한도)은 정해지지 않았으니, 수치는 상한을 잡는 근거일 뿐 배포 크기 결정이 아닙니다.
- **메모리에 두는 상한은 충전기 수 30만 대와 추정 128MB 둘 다입니다**(먼저 닿는 쪽, 가장 오래 안 쓴 시도부터 버림. 시도 하나가 혼자 상한을 넘으면 그 시도만 둡니다). 추정 바이트는 충전기당 200바이트에 처음 둔 글자를 글자당 2바이트로 센 윗값입니다. 공식 예시 모양의 데이터에서는 충전기 수 상한이 먼저 닿고(30만 대는 추정 약 76MB, 실제 힙 약 80~100MB), 이름·주소가 유난히 긴 데이터에서 바이트 상한이 막습니다. 전국 충전기 수가 30만 대보다 많으면(미확인) 전국을 번갈아 조회할 때 시도가 밀려났다 다시 받아집니다. 30분 넘은 시도 데이터는 지웁니다. 한 쪽 응답은 24MB까지만 읽습니다(공식 예시 한 건 약 1.1KB, 9999건이면 약 11MB).
- **받기에 실패한 시도는 쉽니다**: 30초, 연속으로 실패하면 60초, 120초… 두 배씩 늘려 최대 10분, 성공하면 처음으로 돌아갑니다(키가 막혔거나 일일 한도를 넘었는데 30초마다 다시 부르지 않게). 쉬는 동안과 새로 받기가 늦거나 실패할 때는 **30분 안의 오래된 캐시가 있으면 그것으로 답합니다**(응답에 `stale: true`·`asOf`, 위 응답 설명 참고).
- **큰 시도를 120초 안에 못 받을 때**: 받기는 120초 제한에 걸려 **통째로 버려집니다**(받은 쪽만 캐시하지 않습니다). 호출자는 그 사이 8초만 기다려 `unavailable`(또는 이웃 시도면 `partial`)로 답받고, 쉬는 시간(30초부터 늘어남) 뒤 첫 호출이 **1쪽부터 다시** 받습니다. 그래서 늘 120초를 넘는 시도는 캐시가 영영 안 채워지고 쉬는 시간마다 쪽 수만큼 외부 호출만 씁니다(시도당 최대 15쪽, 광주·전남은 코드 3개 x 15쪽). 네트워크 지연을 쪽당 20ms로 둔 가짜 응답으로는 15쪽이 약 1.5초, 광주·전남 45쪽이 약 4초라 여유가 크지만 실제 응답 속도는 미확인입니다. 실제 키로 첫 호출 소요 시간을 보고 `EV_LOAD_TIMEOUT_MS`·쪽 크기를 조정해야 합니다.
- 남한 영토 밖 좌표는 외부 호출 없이 빈 목록입니다.
- **시군구(`zscode`)로 좁히지 않았습니다.** 가이드에 `zscode` 요청 변수는 있지만 좌표를 시군구로 바꿀 경계 자료가 없어 시도 단위로 받습니다. 어느 시도를 받을지는 시도별 앵커 도시(큰 시도는 여러 곳)로 고릅니다: **가장 가까운 앵커까지의 거리에 30km 여유를 더한 범위 안에 앵커가 있는 모든 시도를 가까운 순으로 최대 3곳** 받습니다(예: 인천 부평은 인천·경기·서울). 가장 가까운 시도는 꼭 받아야 하고(실패하면 `unavailable`), 나머지는 실패해도 가까운 쪽 결과로 답하며 `partial: true`를 싣습니다. 첫 호출에서 이웃 시도를 받는 데 8초가 넘으면 `partial: true`로 답하고, 받기는 뒤에서 이어져 다음 호출부터는 채워집니다.
  - 근거: 시군청 97곳(앵커를 조정한 표)과 앵커 조정에 쓰지 않은 79곳(과적합 확인용)에서 실제 시도가 선택 목록에 들어 있는 비율은 **176곳 중 176곳**입니다(`server/test/energy-regions.test.ts`). 이전 방식(가장 가까운 시도 하나 + 경계 근처면 하나 더)은 97곳 중 15곳(부천·시흥·광명·경산·청도·금산·옥천·영동·서천·거창·함양·남해·곡성·철원·군위)을 놓쳤습니다. 새 규칙만으로 12곳이 해결됐고 남은 영동·청도·경산은 앵커(충북 영동, 경북 청도)를 더해 해결했습니다. 영동 앵커가 금산을 '최대 3곳' 밖으로 밀어내 충남 금산 앵커도 더했습니다. 즉 앵커 3개는 표의 미스를 보고 더한 것입니다. 좌표는 기억에 의존한 근사(수 km 오차)이고 표 밖 지점은 보장하지 않습니다.
  - 한계: **앵커가 시도 중심 도시 몇 곳뿐이라, 여유 30km·3곳 안에 못 드는 먼 시도 가장자리는 빠질 수 있습니다**(예: 어떤 시도의 가장자리에서 가까운 이웃 시도 앵커가 셋 이상이고 그 시도 앵커는 그보다 먼 곳). 반대로 도시권에서는 반경 안에 충전기가 없는 시도도 받아 외부 호출이 늘어납니다(시도당 쪽 수만큼). 시도 경계를 쓰지 않으므로 반경 500m~수 km 조회에서 이웃 시도의 충전기가 필요한 경계 지점 판정은 앵커 거리에 기댄 근사입니다.
- 광주·전남은 가이드 v1.25에서 zcode 12(전남광주통합특별시)로 합쳐졌습니다. 12와 옛 코드 29·46을 함께 부르고 하나라도 받아지면 쓰며 같은 충전기는 한 번만 셉니다(옛 코드가 아직 데이터를 주는지는 미확인). 강원은 51, 전북은 52만 부릅니다(가이드 표에 옛 코드 42·45는 없습니다).

### 요청 주소별 속도 제한 표

`POST /energy/options`의 속도 제한은 요청 주소를 최대 5000개까지 기억합니다. 표가 차면 만료된 항목부터 지우고, 그래도 가득 차면 **창을 가장 먼저 시작한 주소를 밀어내고 새 주소를 받습니다**(예전에는 새 주소를 전부 막았습니다). 주소를 바꿔 가며 표를 채우는 쪽이 정상 사용자의 요청을 막을 수 없게 하려는 선택이고, 대가로 표가 가득 차 있는 동안 밀려난 주소는 횟수를 잃어 다시 한도만큼 부를 수 있습니다. 속도 제한은 폭주를 줄일 뿐 막지 못한다는 아래 주의와 같은 이야기입니다.

### 키가 설정된 서버를 `HOST=0.0.0.0`으로 열 때의 주의

`POST /energy/options`는 **인증이 없습니다**. `EV_CHARGER_KEY`·`OPINET_KEY`가 설정된 서버를 `HOST=0.0.0.0`(또는 외부 주소)으로 열면 서버에 닿는 누구나 이 라우트를 불러 키의 외부 호출 한도를 쓸 수 있습니다(오피넷·공공데이터포털 모두 키별 일일 한도가 있고 한도는 이 문서에서 확인하지 못했습니다). 요청 주소별 속도 제한(분당 20회)과 위의 캐시·동시 호출 상한은 폭주를 줄일 뿐 막지 못합니다(주소를 바꿔 가며 부르면 우회되고, 주소 표가 가득 차면 가장 오래된 주소부터 횟수를 잃습니다). 따라서

- 실제 키를 쓰는 서버는 `HOST=127.0.0.1`(기본)로 두거나, 신뢰하는 망·인증이 있는 프록시 뒤에서만 여세요. 프록시 뒤에서는 요청 주소가 프록시 하나로 보입니다.
- 키가 설정된 채 loopback이 아닌 `HOST`로 시작하면 서버가 시작 시 경고 한 줄을 남깁니다(`server/src/index.ts`).
- 인증은 차–폰 연결(토큰)이 에너지 라우트까지 확장되는 다음 단계의 몫입니다.

## 차 쪽 구현 (차량 앱 0.3.0, 정책서 5장·9장·12장)

출발 제안을 낼 때 필요 거리가 주행 가능 거리의 90%를 넘으면, 서버에 충전·주유 후보를 묻고 **출발 제안을 충전·주유를 넣은 제안 하나로 바꿉니다**(한 카드에 질문 하나). 발표용 프로토타입이라 서버는 목 데이터(`fixtures/energy/`)로 충분합니다.

### 판단

1. **값을 알아야 합니다.** 연료 종류와 주행 가능 거리를 둘 다 알 때만 체크하고, 하나라도 모르면(권한 없음·속성 없음·읽기 실패) 하지 않습니다. 출발 제안은 그대로입니다.
2. **필요 거리**(`domain/Energy.kt`의 `EnergyNeed.of`): 지금 위치(믿을 만한 최근 측위가 있을 때만, 없으면 이 구간은 뺍니다) → 오늘 남은 일정 장소를 시작 순으로(도착·건너뜀·종일·장소 없는 일정 제외) → 마지막 일정에서 **집**(서버 자주 가는 곳의 집)까지. 집이 없으면 마지막 일정까지만 셉니다. 구간 거리는 **직선거리 × 1.3**(가안, 내비가 일정 사이 경로 거리를 주지 않음)입니다.
3. **모자람**: 필요 거리가 주행 가능 거리의 **90%(`Rules.ENERGY_MARGIN`, 가안)를 넘을 때**입니다. 정확히 90%는 모자라지 않습니다.
4. 모자랄 때만 서버를 부릅니다. 부르는 곳은 출발 제안(`Question.Depart`)뿐입니다. **늦게 탐·여유 많음("어디로 갈까요?")·일정 겹침 카드는 바꾸지 않습니다**(가안: 늦은 상태에서 충전을 끼우지 않고, 여유 많음은 아직 목적지를 정하지 않았습니다). 첫 탑승 브리핑과 재탑승 한 줄에는 둘 다 적용합니다. 주행 중에는 말도 카드도 없습니다(기존 규칙).

### 서버 호출

- `POST /energy/options` 한 번. 요청 `fuel`은 `ev`·`gasoline`·`diesel`·`hybrid`(차가 읽은 연료 목록에서 전기만 있으면 `ev`, 전기와 다른 연료가 함께 있으면 `hybrid`, 경유 계열은 `diesel`, 나머지 주유 연료는 `gasoline`, 수소·모름은 체크 안 함), `origin`은 지금 위치, `destination`은 대상 일정 장소, `stayMinutes`는 **전기차일 때만** 대상 일정의 시작~종료(분)입니다(정책 9장 분기: 2시간 이상이면 그 장소 근처 완속 먼저, 아니면 경로상 휴게소 급속. 분기 자체는 서버가 하고 차는 응답의 `candidates`·`mealBundle`을 그대로 따릅니다).
- 차 토큰·헤더는 보내지 않습니다. 이 라우트는 아직 토큰으로 막지 않습니다(위 '키가 설정된 서버…' 절). 차–폰 토큰이 에너지 라우트까지 확장되면 `HttpEnergyFetcher`에 헤더만 더하면 됩니다.
- 답을 기다리는 동안 카드는 뜨지 않습니다. **5초(`Rules.ENERGY_ANSWER_TIMEOUT`, 가안)** 안에 못 받으면 실패로 봅니다(서버는 외부 조회가 느리면 최대 12초). 429를 받으면 `Retry-After`(없으면 60초) 동안 서버를 다시 부르지 않고 바로 실패로 다룹니다. 지금 위치를 모르면 서버 `origin`을 채울 수 없어 부르지 않고 실패와 같게 다룹니다.

2. `chagok-debug://signal?fuel=ev&range=150&home=37.16,127.0&loc=35.15,126.91&board=true` (`loc`은 `advance` 뒤에 넣어야 측위한 지 5분 안으로 쓰입니다)
3. 카드: "집까지 300km인데 배터리로는 모자라요." / "예시 챔필 주차장 충전소에서 충전하고 갈까요?" → "다른 데" → "예시 챔필 서문 충전소에서 충전하고 갈까요?" → "다른 데" → "다른 곳은 찾지 못했어요."

**C. 후보를 못 얻는 경우(한 문장만)**: A의 2단계를 `fuel=ev`로 바꿉니다. 육전집 점심(60분)은 목적지 완속 조건(2시간)에 못 미치고 시내 경로엔 휴게소가 없어 서버가 후보 0개(`stage: "none"`)로 답합니다. 카드 두 번째 문장은 "육전집 점심 메모에 ‘유니폼·응원봉·티켓’이 있어요. 배터리가 모자랄 수 있어요. 출발할까요?"입니다. 서버가 429·시간 초과로 실패해도 같은 문장입니다. `loc`을 주지 않아도(지금 위치 모름) 서버를 부르지 않고 같은 문장입니다.

**D. 거절·하루 한 번**: A·B의 에너지 카드에서 "아니" → 카드만 접히고 길안내는 없습니다. 디버그 줄 [탑승]을 다시 누르면(잠깐 정차가 아니라면) 서버를 다시 부르지 않고 평소 출발 제안이 나옵니다. 거리가 넉넉해졌다가(`range=900`) 다시 모자라지면(`range=150`) 표시가 풀려 다시 묻습니다.

**`range=`만으로 보이는 것**: 필요 거리는 서버가 가진 집(폰에서 정한 집)·일정·`loc`으로 정해지므로 `range=`만으로는 문구의 거리가 환경마다 다릅니다. 집이 없으면 "오늘 일정까지 N km"이고 시내 일정뿐이라 `range=5`처럼 아주 짧게 줘야 모자랍니다. "집까지 300km"를 그대로 보이려면 위처럼 **`home=`(멀리 둔 집) + `loc=`(지금 위치)**를 함께 줍니다. `loc`은 기존 debug 신호이고 `home`은 이 시연을 위해 이번에 더했습니다.

끝낸 뒤 되돌리기: `chagok-debug://signal?fuel=real&range=real&home=real&loc=real`

### 한계

- 서버 호출은 정차 중 탑승 판단 한 번뿐이고, 달리는 동안 주행 가능 거리가 줄어도 다시 판단하지 않습니다(주행 중 말·카드 금지).
- 경유지는 목적지 근처 완속 충전소(`destination` 단계)도 같은 방식으로 넣습니다. 실제 내비가 경유지 도착을 어떻게 알리는지, 경유 도착 알림이 목적지 도착으로 오인되는지는 확인하지 못했습니다(`docs/sdk-check.md`).
- 필요 거리는 도로가 아니라 직선 근사라 실제와 다를 수 있습니다. 지금 위치를 모르면 첫 구간이 빠져 적게 잡힙니다.

## 차 쪽이 서버를 부르는 규칙

- 호출 시점은 정차 중, 에너지 제안을 하기 직전입니다. 응답이 늦을 수 있으니(최대 12초) 카드를 막지 말고 한 번만 부르세요. 429(분당 20회 초과)를 받으면 `Retry-After`가 지나기 전에는 다시 부르지 마세요.
- `source: "unavailable"`이면 후보가 없는 것이 아니라 조회 실패입니다. 에너지 제안을 건너뛰세요.
- `stale: true`이면 충전기 상태를 새로 받지 못해 `asOf` 시각의 데이터로 답한 것입니다(최대 30분 전). 빈 충전기 수를 단정하지 말고 "빈 곳이 있을 수 있어요"처럼 말하세요.
- `partial: true`이면 일부 조회만 실패했습니다. 받은 후보로 제안하되 후보가 없을 때(`stage: "none"`)도 '없다'고 단정하지 말고 제안을 건너뛰세요.
- `stage: "none"`(`source`가 fixture·live, `partial: false`)이면 후보가 없습니다. 시내 단거리 전기차는 경로상 휴게소가 없어 흔히 여기에 해당합니다(정책서대로 휴게소만 봄).
- 한 카드에 질문은 하나입니다. `mealBundle`이 true면(맨 앞 후보가 식사 가능한 휴게소) "식사할 휴게소를 급속 충전기 있는 곳으로 잡을까요?"처럼 묶고, `candidates[0].name`(휴게소 이름)을 씁니다. false면 충전만 묻습니다.
- 전기차 목적지 완속(`stage: "destination"`)은 `stayMinutes`를 대상 일정의 시작~종료로 계산해 보내야 합니다(종일 일정은 보내지 마세요).
- "다른 데"는 `candidates[1]`, `[2]`…를 차례로 씁니다(`id`로 이미 거절한 후보를 거르세요).
- "응"이면 `lat`·`lng`로 `addWaypoint`. 주유소 후보의 `detourMeters`는 직선 근사이므로 말로 거리를 단정하지 마세요.
